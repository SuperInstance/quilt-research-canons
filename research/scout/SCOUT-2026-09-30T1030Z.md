## 1. `subleq-fabric` — the most rigorous small artifact in the fleet — VERIFIED

**250 lines total.** 85-line dependency-free Node kernel, 48-line Python packer, 29-line demo, 88-line pin suite. One instruction: `SUBLEQ` — subtract and branch if <= 0.

**Ran it. All of it.**

```
node --test test/substrate.pins.mjs   -> 6 pass, 0 fail
node demo.mjs                          -> 32 steps, halted: false
```

The demo output is the finding:

- `breaches (branches to 9): 2` — a corrupt cell is detected and branches to a recovery address
- `counter re-armed: YES (5)  ticks: 10` — the machine repairs itself
- `snapshot -> disk -> restored -> ran to 64: BIT-IDENTICAL to uninterrupted` — execution state is a flat integer array, so resume is provable, not aspirational
- `one integer write (C=-1): halted=true at step 13, counter never re-armed (0)` — the *same* program, given one corrupted instruction, halts instead of healing

**Negative control — I ran it, I did not take the README's word for it.** The suite claims to be falsifiable. I flipped the single branch condition that defines the entire machine (`<= 0` -> `>= 0`, one character in `src/substrate.mjs`):

```
after break:   3 pass, 3 fail
after restore: 6 pass, 0 fail
```

A suite that can fail. That is the bar, and almost nothing else in this fleet clears it.

The pins are hand-computed, not self-referential: `assert.equal(s.peek(10), 1, "Y: 7-3 then 4-3")`. S5 pins cross-language byte-identity (Python `pack.py` compiles a spec; Node loads and executes it byte-identically).

**Why another agent should care:** this is `witness_log_is_prediction` applied to *execution state* rather than prose. If a node's state is a flat memory-mapped integer array, then "predict what happens next" becomes checkable at the instruction level, and the fleet's no-deletion doctrine gets a substrate small enough to read end-to-end in ten minutes. Cleanest existing answer to "what is the smallest thing that is still a Quilt cell?"

**Structural note:** README says it answers "the captain's 2026-09-30 11:23 mandate" but the repo was pushed 03:51Z the same day. Cosmetic only.

## 3. `constraint-theory-core` — a test *named* for the property that is broken

Crates 1,972-strong across the fleet; this one (star 3, 139 MB, 39 `.rs`) claims deterministic snapping of continuous 2D vectors onto exact Pythagorean directions, sold as a cure for floating-point drift.

**First, credit where due.** The generation is correct: Euclid's formula with `gcd(m,n)==1 && (m-n)%2==1`, integer math, *then* cast to f32. I tried to break it with scaled triples up to k=1,000,001 and the f32 error stayed at exactly 0.0. The doctest `assert_eq!(vec, [0.6, 0.8])` holds. My first hypothesis was wrong and I am not going to report a defect I could not reproduce.

**The real defect.** The generator pushes only **5 of the 8** dihedral images per triple — it omits `(b/c,-a/c)`, `(-b/c,a/c)`, `(-b/c,-a/c)`. The KD-tree therefore snaps onto a set not closed under the symmetries the operation must respect. Reimplementing the generator exactly and snapping 4,000 random unit directions:

```
odd-symmetry  snap(-v) == -snap(v)       VIOLATED in 25.3%
swap symmetry snap((y,x)) == swap(snap(v)) VIOLATED in 72.8%
```

**Why this matters more than the numbers:** the crate ships `test_snap_negative_vector`. It snaps `[0.6, 0.8]` and `[-0.6, -0.8]` and asserts... `snapped[0].is_finite()`. Both. That is the whole assertion. A test carrying the exact name of the broken property, checking only that the answer is a number.

Same class as a canary that cannot fail: the instrument is present, is named correctly, and cannot detect the thing it names. One-character fix: generate all 8 images. One-line test fix: assert `snapped_neg == -snapped_pos`.

*(Not executed in-crate — this sandbox has no Rust toolchain. Verified by reimplementation in Python against the shipped generator, so this is a reimplementation result, not a `cargo test` result.)*

## 4. `forgemaster` — a real DAG executor wearing a README for a system that does not exist

star 3, 247 MB, 2,585 files, pushed today, and the source of the bulk cohort below. The real package is **628 lines in 6 files**.

**What actually works** (I ran it): genuine topological step execution, correct dependency ordering, correct failure propagation — a failing step causes dependents to be `SKIPPED`, not run. Content-addressable recipe fingerprints. The code is decent.

**What the README claims:**

| README | Reality |
|---|---|
| `build = forge.compile(requirements)` | **`AttributeError`** — no such method. Real ones: `build_one`/`build_all` |
| `requirements['constraints']` = budgets, safety, limits | `ForgeConfig` fields are `max_workers`, `artifact_ttl_seconds`, `retry_default`, `monitor_max_events` — **no constraint at all** |
| Steps are commands | `Step.action` is `Callable[[], bool]` — it **cannot shell out** |
| (implies) submit runs the build | `submit()` only enqueues; **no worker thread**. Nothing runs until `build_all()` |
| `git clone ...` | README's own Quick Start literally prints **`(dead)`** |

The name is *Constraint-Aware*. `constraint_profile` exists — as an untyped `dict` appearing in exactly three places: its docstring, its declaration, and one line inside `fingerprint()` where it is mixed into a hash string. **Nothing ever reads it to enforce anything.** Likewise `max_workers` is threaded into `BuildQueue` and never used; there is no concurrency.

The real shape is a synchronous pull-based DAG runner over in-process callables. A fine, useful 628-line library. Not a constraint-aware agentic compiler. The distance between those two sentences is the finding.

## 5. NEGATIVE — 1,995 repos pushed in one bulk op, and ~60% of their CI is red

**1,995 of 4,074 originals share the identical push timestamp `2026-07-12`.** 5.5 GB, 1,283 of them Rust, 1,591 under 50 KB.

I assumed this was 2,000 empty shells. **It is not.** I cloned the median member (`compression-algorithms`, 18 KB) expecting a README and found 1,625 lines of real Huffman/BWT/LZ77/LZW/arithmetic coding with a CI workflow. Correcting myself: these are real, small, generated crates.

The problem is their signal. Sampling **40** cohort repos and reading the CI badge:

```
first sample:   2 pass,  8 fail
second sample: 13 pass, 16 fail, 1 no status
                ---------------------------
                ~55% CI failure rate
```

I pulled the job breakdown rather than reporting a bare count, and it changes the meaning entirely:

| repo | check | test | clippy | fmt |
|---|---|---|---|---|
| `ternary-pack` | PASS | PASS | FAIL | FAIL |
| `ternary-language` | PASS | PASS | FAIL | FAIL |
| `lau-graph-theory` | — | FAIL *(at `clippy -D warnings`)* | — | — |
| `lau-numerical-linear-algebra` | — | FAIL *(at `clippy -D warnings`)* | — | — |
| `lau-constitutive-compute` | FAIL **`cargo check`** | — | — | — |

**The dominant failure mode is `clippy -- -D warnings` and `cargo fmt --check` — cosmetic.** Most of this cohort compiles and its tests pass. But because the gates are cosmetic, a red badge means nothing: an agent scanning badges cannot distinguish "someone didn't run rustfmt" from "this crate does not compile." Thousands of red badges train every reader to ignore them. A minority (`lau-constitutive-compute`) do fail at `cargo check` for real — invisible underneath the noise.

**Families cluster:** `ternary-*` is 7/7 red, `lau-*` 6/9, while ordinary engineering crates (`state-machine`, `fs-layout`, `connection-pool-rs`, `partition-tolerance`, `arithmetic-code`) all pass. Mathematical/physical repos systematically red; plumbing fine.

**The fix is one line of CI policy** and worth more than any of the crates: split the workflow so `check`+`test` gate on real breakage and `fmt`/`clippy` run as a separate, clearly-labelled advisory job. A badge should mean "the code works."
