## 1. `capability-spec` — 200 real tests; CI has never run one, and says "No tests" every push

**The gem:** a formal capability-specification language for agents — TOML declarations, schema
validation, capability matching, topological dependency resolution, an A2A adapter, fleet
discovery. Zero external deps (stdlib + `tomllib`). This is the best-structured repo in the batch
and the only one whose whole design is machine-readable *fleet self-description*.

**Its 200 tests pass.** Executed under a local pytest shim (PyPI unreachable): **200 passed**.

### The gate: `ci.yml:20`

```yaml
- run: pip install pytest && python -m pytest tests/ -v --timeout=60 2>/dev/null || echo "No tests — syntax check passed"
```

Three independent faults, compounding:

1. **`--timeout` is not installed.** Only `pytest` and `pyyaml` are installed. `--timeout` ships
   with the `pytest-timeout` plugin, which is *not* in the install line. pytest's argparse
   rejects it: `unrecognized arguments: --timeout=60`, exit code **4**.
2. **`2>/dev/null` hides the only error message** that would explain what happened.
3. **`|| echo` converts the failure into a false statement about the repository** and exits 0.

Replayed verbatim against a stub reproducing pytest's USAGE_ERROR exit:

```
=== EXACT ci.yml line 20 (as written, WITH --timeout=60) ===
No tests — syntax check passed
   job exit: 0
=== same line WITHOUT the flag — 200 tests would really run ===
collected 200 items
   job exit: 0
```

So the repo prints **"No tests — syntax check passed"** on every push, and it has 200 passing
tests. This is worse than `|| true`: `|| true` is at least silent. This one *asserts a falsehood
about the codebase*. `ci.yml:19` is a separate `ast.parse` sweep, also `|| true`.

### Why another agent should care

This is the highest-leverage item in the report. A 200-test spec language that other agents will
build on, whose CI reports zero tests, is a **green checkmark that actively misinforms**. The
`|| echo` shape is worse than the `pytest || true` class already in the fleet's records, because
it converts a *tooling* error into a *claim about the code*.

### Separately: `fleet_discovery.py:16` reads the whole `.bashrc` into a variable named `GITHUB_TOKEN`

```python
GITHUB_TOKEN = open(Path.home() / ".bashrc").read()      # line 16, unguarded
for line in GITHUB_TOKEN.split("\n"):
    if "export GITHUB_TOKEN=" in line:
        GITHUB_TOKEN = line.split("=", 1)[1].strip().strip("'\"")
        break
```

- **Import-time crash.** No `~/.bashrc` → `FileNotFoundError` on `import`. This is why 20 of its
  220 tests error in a clean environment — an environment coupling that CI would have caught if
  CI ran the tests.
- **The fallback leaks the entire shell config.** If `.bashrc` exists but has no
  `export GITHUB_TOKEN=` line, the loop never breaks and `GITHUB_TOKEN` stays bound to the
  **whole file** — every alias, and any other secret in it. That string is then sent as
  `Authorization: token <entire .bashrc>` to `api.github.com` on every request (lines 28, 39).
- **The test suite rewrites the developer's real `~/.bashrc`** (`setup_bashrc` / `_restore_bashrc`
  in `tests/test_fleet_discovery.py`). A crashed or interrupted run leaves it modified.

Not packaged into the wheel — `pyproject.toml` sets `include = ["capability_spec*"]` and this is
a root-level script — so it is not a supply-chain leak, but it is committed and importable.
Also note `fetch_toml` has a bare `except:` returning `None`, so a repo that 403s or 404s is
indistinguishable from a repo with no `CAPABILITY.toml` — fleet coverage silently under-reports.

**The FALSIFIED branch is unreachable.** All 10 harnesses hardcode `outcome="INCONCLUSIVE"` in
the `AuditResult(...)` return. There is no code path anywhere in `test_harnesses/`, `audit.py`, or
`common/` that produces `"CONFIRMED"` or `"FALSIFIED"`. The tri-state verdict the README
describes — "either CONFIRMED / FALSIFIED / INCONCLUSIVE" — is a two-state machine wearing a
three-state costume.

The `critical`-priority conservation harness is the clearest case. It accepts `seed` and
`iterations` and **uses neither** — no RNG is even constructed. Its `evidence` is a dict of
*strings describing measurements that were not taken*:

```python
{"forage_values": "γ+H measurements inside forge (n=100)",   # a str, not 100 numbers
 "expected_if_conserved": "no significant difference between interior and boundary measurements"}
...
notes="Not yet implemented. Requires defining γ and H for each ecosystem."
```

**In fairness:** the tool is honest about its own emptiness — the summary prints `0 confirmed /
0 falsified / 10 inconclusive`, and `status_badge` and the registry's `PENDING` defaults are
truthful. This is an aspirational scaffold, not a fraud. But the README's central sentence is a
claim about a capability the code does not contain.

### The one real experiment is orphaned — and its program space cannot express its target

`test_hardware_agnostic_adaptive_evolution.py` is the only harness with real classes
(`MachineCodeProgram`, `TargetFunction`, `HardwareAgnosticEvolver`, `FixedStrategyEvolver`) and
real experiments. It has **no `run_simulation`**, is **absent from the `CLAIMS` registry**, and is
therefore never run by `audit.py` (the runner reports 10, not 11). Run directly, it works — and
returns a negative:

```
Adaptive speedup: 1.00x
Adaptive wins: 0/3 runs
Learning improvement: 1.00x
```

That "negative result" is not evidence about hardware-adaptive evolution. It is an artifact:

- The generator emits 8 opcodes: `add, compare, sub, mul, div, load, store, halt`.
- The interpreter implements 4: `add, compare, halt, branch`.
- **`sub, mul, div, load, store` — five of eight — fall through silently**, each just `pc += 1`.
- `branch` is implemented but **never generated** — dead code in the interpreter.
- `compare` collapses a register to a boolean: `registers[ra] = 1 if > else 0`. Information is
  destroyed, and `add` can never recover it.
- There is **no conditional control flow in the program space at all** — the program is a
  straight line.

The target is `make_sorting_target` — sort 4 elements. A sorting network requires
compare-and-conditionally-swap, i.e. **branches**. The program class has no branches. The target
is therefore *unsatisfiable by construction*, and the observed fitness ceiling of `0.04` (2 of 50
cases) is the floor, not a measurement. Fitness is flat at 0.04 from generation 0 through 200 in
every run; nothing is evolving.

**Why another agent should care.** This is the fleet's designated self-correction layer, and the
one piece of real evidence it produced was a negative result caused by a stub interpreter — while
the harness that would have caught that was never wired in. A falsification layer that cannot
falsify is the load-bearing absence in the whole self-correction story.

## 3. `grand-pattern-ptx` — a GPU kernel whose reduction reads two of its three arrays from unwritten shared memory

A polyformalism pair (`grand-pattern-ptx` / `grand-pattern-opencl`): 8 identically-named test
files, same input vectors, same expected values, same 0.01 tolerances. The port is **faithful** —
I compared `test_cosine.c` line by line across both, and the OpenCL kernel body is the same
algorithm (block-per-pair, strided loop, local-memory reduction, `cos = dot/(√na·√nb)`). This is
the good kind of polyformalism, and it is worth saying so.

**The defect is in the PTX kernel, and only there.** `src/kernels/cosine_similarity.ptx` declares
`.shared .f32 smem[256]` (valid elements 0–255) and then changes unit convention between the
store and the load:

| | PTX text | byte address | element | range (blockDim=128) |
|---|---|---|---|---|
| write | `st.shared.f32 [idx]`, `idx = tid<<2` | `tid*4` | `tid` | 0–127 |
| write | `st.shared.f32 [idx + 256]` | `tid*4+256` | `tid+64` | 64–191 |
| write | `st.shared.f32 [idx + 512]` | `tid*4+512` | `tid+128` | 128–255 |
| read | `ld.shared.f32 [idx*4]` | `idx*4` | `idx` | 0–127 ✅ matches |
| read | `ld.shared.f32 [idx*4 + 256*4]` | `idx*4+1024` | `idx+256` | **256–383 ❌ never written** |
| read | `ld.shared.f32 [idx*4 + 512*4]` | `idx*4+2048` | `idx+512` | **512–639 ❌ never written** |

The writes use `+256`/`+512` as **byte** offsets (one float past `idx = tid*4`); the reads use
`+256*4`/`+512*4`, i.e. **element** offsets scaled to bytes. `fnorm_a` and `fnorm_b` are
therefore summed from shared memory that was never written, 128 and 256 floats past the end of
the array. `cosine = dot / (√norm_a · √norm_b)` divides by two garbage sums.

This is **live, not latent**: `test_cosine.c` launches with blockDim 128 and asserts
`sim == 1.0 / 0.0 / -1.0`, which is exactly the path through the broken reduction.

**Localization:** 1 of 7 PTX kernels. The other six do not use this pattern. `cosine_similarity.ptx`
is also the only file still carrying a `shfl.down.b32 ... // placeholder — real reduce below`
instruction whose result is discarded.

**Not executed — no GPU in this sandbox** (`nvidia-smi` absent). The analysis is static and the
arithmetic is shown above so it can be checked; I am not claiming a reproduced crash.

**CI, honestly labelled:** both repos carry the untouched template
`run: echo "No CI configured — customize per project requirements"`. Inert, but it says so —
unlike item 1.

## 4. `si-runtime-python` vs `si-runtime-go` — the same-named conservation law enforcing two different things

A textbook polyformalism pair: identical module inventory in both languages —
`agent, capability, cell, conservation, fleet, spectral`, each with a test. The Go side is
unexecutable here (no Go toolchain), so **the Go claims below are inspection only**; the Python
side was executed and mutated.

They are not ports. They are different models wearing the same names.

| | Go `conservation.go` | Python `conservation.py` |
|---|---|---|
| state | `Budget{Total, Gamma, Eta}` | `Budget{total, gamma, eta}` (static) + `AgentBudget{_allocated, _spent}` |
| allocation | `Allocate(gamma, eta)` sets both atomically | `allocate()` touches `_allocated` only |
| invariant test | `gamma+eta != Total` — **exact float equality** | `abs(gamma+eta-total) < 1e-9` |
| transfer | moves **Gamma** between agents | moves **unspent allocation** via spend/allocate |
| audit | sums fleet-wide, reports `Valid` | returns a list of `Violation` |

### The Python law is a constructor assertion on decorative fields

`allocate()` and `spend()` **never write `gamma` or `eta`.** Executed:

```
=== do allocate/spend/transfer ever touch gamma or eta? ===
  start           gamma=60.0 eta=40.0  _alloc=0.0   _spent=0.0
  after full use  gamma=60.0 eta=40.0  _alloc=100.0 _spent=100.0
  -> gamma/eta MUTATED? False
  -> validate_budget still: True   (law "enforced" after 100% consumption)

=== audit() on two agents with wildly different real usage ===
  drain consumed 100/100 capacity; idle consumed 0/100
  audit() violations = []   -> reports CLEAN: True
```

`transfer()` ends with a loop labelled "Verify invariant still holds on both sides" — it
validates a field pair the transfer operation did not modify. It can only fire if the budget was
**constructed** invalid, i.e. before any code ran:

```
  agent did normal work (alloc 50, spend 10) on a budget whose gamma+eta=0 != total=100
  audit() = [Violation(agent_id='bad', expected=100.0, actual=0.0, delta=100.0)]
  -> violation was true before any code ran. The law is a constructor assertion,
     NOT a conservation law over the resource flow.
```

So `γ + H = constant` — the fleet's central conservation claim, and one of the four
`priority: critical` claims in `dog-food-audit` — is, in the Python runtime, an assertion about
two fields that no runtime path maintains. Consumption is invisible to the auditor.

### The tests are honest — this is a coverage gap, not a fake suite

Baseline **33 passed** (1 further failure is my shim lacking `parametrize` support, not a repo
defect). All three mutations went RED and restore returned green:

| mutation | result |
|---|---|
| `validate_budget` → `return True` (law deleted) | **RED** — `test_invalid_budget` |
| `audit` → `return []` (auditor blinded) | **RED** — `test_audit_violation`, `test_fleet.test_conservation_audit` |
| drop overspend guard in `spend()` | **RED** — `test_spend_exceeds_allocation` |

md5 restored: `0781c97e7216b3de05202c232b6b2131`. The suite tests the functions in isolation; it
never tests that the law constrains the flow. That distinction matters — report it as a design
disconnect, not a fabricated suite.

### And the CI cannot fail either

`si-runtime-python/.github/workflows/ci.yml:19` — `- run: pytest || true`, across a 3.10/3.11/3.12
matrix. A vacuous law behind a fail-open gate. The Go side's CI is a bare `go test ./...` with no
`|| true` — honest, and unverifiable here.
