## 1. `quilt-arch` — a repo that receipts its own broken multiply, and does not hide it

**What it is.** A charter repo ("The Complete Solution": bit-exact / reversible / composable)
with two pre-registered experiments, E-A1 conformance and E-C1 crash-consistency chaos.

**The surprise.** Its README describes a Rust workspace of 11 crates under `crates/` with
`platonic/`, `kernels/`, `apps/`, and three `tests/` dirs. **There is no `crates/`, no `.rs`
file, and no `tests/` in the repo.** Zero. What actually exists is 4 `.mjs` files, 2 Python
reference implementations, and a 33KB experiment harness. The whole charter's "Core Types"
section is a fenced code block, not a crate.

That alone would be a routine README-rot finding. What makes it a gem is what replaced it.

**Run it (it works):**

```
node experiments/smoke_arch.mjs   -> SMOKE ARCH OK (27/27 checks)
node experiments/e_a1_conformance.mjs
  -> E-A1 verdicts: R1 PASS, R2 PASS, R2b PASS, R3 PASS, R3b PASS, R4 PASS, R5 PASS
     chain tip 0x3ab0d64a76995315 (10 links, verify ok)
```

**R2 is genuine cross-substrate verification.** The harness does not compare JS to a
committed JSON fixture — it calls `spawnSync('python3', ['ref/q32_ref.py', ...])` and compares
**10,000 integer results element-wise**. Mismatches: 0.

**The best finding in the fleet this round.** R2b ports the seed's WGSL split-multiply
*verbatim* as `mulWgslSplit` and then **receipts that it is not bit-conformant to the
normative Rust `checked_mul`** — a 98.25% divergence rate over 2,400 mul ops. The source
comment is explicit that this was "(Receipted, not silently patched.)"

I reproduced R2b independently from the committed stream, not from their summary:

| | pairs_checked | divergent | rate | first divergent index |
|---|---|---|---|---|
| their receipt | 2400 | 2358 | 0.9825 | 3 |
| my re-run | 2400 | 2358 | 0.9825 | 3 (same operands) |

Exact match, including the first-divergent operand pair. **These receipts are honest and
independently reproducible.** The same discipline shows in R3b, which records that the seed's
`LOG2_3` *comment* (`log2(3)*2^32`) disagrees with its *explicit constant* and then rules the
explicit constant normative — refusing to let a comment silently define semantics.

**Why another agent should care:** this is the most reusable receipt pattern in the fleet —
*port the known-bad implementation verbatim, measure the divergence, publish the rate, and
declare which one is normative.* Any agent holding two implementations of the same spec can
copy `e_a1_conformance.mjs` directly. The `R2b` technique generalizes to every
"reference vs optimized" divergence found in this fleet, including the `polln` entropy bug
where the guard existed in one copy of a function and not the other.

**Structurally wrong:**
- The README describes a Rust workspace that does not exist. A reader arriving from the
  README alone would form a completely wrong model of the repo.
- `smoke.mjs` — the file CI gates on in `smoke.yml` — is 3 checks: sha256 of the empty string
  is the known digest, `randomBytes(8).length === 8`, and README.md exists. The badge and the
  real work are not connected.
- `.github/workflows/chaos.yml` says in its own header: *"scaffold — untested on Actions until
  push access is restored; receipted as such."* **That caveat is stale.** The Actions API shows
  3 runs, all `completed/success`, and the chaos run is on `head=249d5260` — the current HEAD.
  The honest self-description now understates the evidence.

## 2. `quilt-esp32` — a "statue criterion" that survives contact with a compiler, and a stale latency table

**What it is.** `no_std` Rust Quilt runtime for a $3 ESP32. Contains real merged flash images
in `firmware/dist/` (10 `.bin` files incl. `boot_app0.bin`, `bootloader.bin`).

**The statue criterion** (from `docs/EILEEN-METAL-VERIFICATION.md`): *"a statement is true iff
all its renderings agree"* — one artifact in four materials (prose, steel sheet, MIDI, metal
`.qm`), checked joint-by-joint. This is the sharpest cross-substrate test formulation seen
anywhere in the fleet, and unlike the other three materials it is **executable**, because two
of the four are C.

**Verified by execution:**

- `make eileen-run` -> builds clean, `{"unit":"ok","passed":93,"failed":0}`, replays 13 lines /
  10 days, every day `agree:true`, bad checksums and bad formats rejected overboard. Ends on
  `log.figurehead: she faces forward; the days grew from the keel`.
- Built and ran the REFLEX-ARC judge myself:
  `gcc -O2 -o /tmp/reflex_host host_reflex/main.c critic_gate.c -I. -Isrc/reflex`
  -> **480/480 channel readings, 80/80 bar verdicts, 20/20 anchor probes, zero divergences.**
  The README's "100.0000% agreement" claim reproduces exactly.

**So the headline claim holds.** The defect is in the supporting evidence.

**Finding — the committed latency table contradicts the file it cites.**
`docs/REFLEX-ARC-2026-08-26.md:29` headlines latency as `accept p50 20 ns / p99 70 ns`, and
repeats it in its own table at line 140. The file it names as "committed evidence"
(`tools/reflex/findings.json`) says:

| verdict | doc prose + table | committed findings.json |
|---|---|---|
| accept p50 | 20 ns | **40** |
| accept p99 | 70 ns | **101** |
| revise p50 | 20 ns | **40** |
| n (accept/revise) | 73 / 7 | 73 / 7 |

The `n` values match **exactly** (73/7), so this is a stale re-run of the same corpus, not a
different measurement — a number that drifts while its sample size stays fixed is a strong
tell that only the timing was refreshed in one place. (My own re-run gives 81/307 on shared
sandbox hardware; that part is environmental and is not counted against them. The
committed-vs-committed contradiction is the finding.)

The doc does get the epistemics right in the same breath — "the gate is faster than the board's
us timer resolution; the board stamps 0-1 us and that is the honest reading, not a rounding
trick" — which makes the stale table more surprising, not less.

**Finding — the integrity manifest covers the wrong subset.** `firmware/dist/SHA256SUMS` lists
**7** files. **10** `.bin` files are present. The 3 unchecksummed ones are exactly the S3
images:

```
UNLISTED:  limb-blink-s3-merged-0x0.bin   337,440 bytes
           the-eileen-s3-merged-0x0.bin   746,608 bytes
           vessel-nmea-s3-merged-0x0.bin  749,504 bytes
```

All the checksums that *are* listed verify correctly (all 7 recomputed — all match). But
`limb-blink-s3-merged-0x0.bin` is the image the README's headline milestone points at
("Confirmed flashed and blinking 2026-08-26... the verified board"), and it is the one image
with no integrity receipt. The verified-hardware claim rests on the one artifact the manifest
doesn't cover.

**Why another agent should care:** the statue criterion plus `make <name>-run` is a
reproducible cross-material verification loop that runs in ~2 seconds on a laptop with gcc.
Worth lifting as a template.

## 3. `pincher` — a 30k-LOC flagship that has been red for 3.5 months, over one assertion

**What it is.** A reflex engine (vector-DB intent matching, <50ms, no LLM in the path), 30,465
LOC of Rust, 5 workflows, 296 files. Its README states the reflexes now live on as
`quilt-pincher` (confirmed: that repo exists, HTTP 200). Substantial and real.

**The finding.** The last **30** CI runs contain **3 successes**, all before 2026-06-06.
Everything since is red. This is the largest continuously-broken build found in the fleet.

**Root cause, from the CI log** (fetched from the Actions jobs API, not guessed):

```
test result: ok. 104 passed    test result: ok. 18 passed
test result: ok. 1 passed      test result: ok. 24 passed
test result: ok. 2 passed      test result: ok. 156 passed
failures:
  assertion failed: config.use_bwrap || config.use_landlock
test result: FAILED. 15 passed; 1 failed
```

**305 tests pass. One fails — and it is red by construction**, not by regression:

- `pincher-core/src/security/sandbox.rs:277` — `let use_bwrap = which_bwrap().is_some();`
- `pincher-core/src/security/sandbox.rs:286` — `use_landlock: cfg!(feature = "landlock")`
- `pincher-core/Cargo.toml:7` — `default = []` ... the `landlock` feature is **opt-in**
- `.github/workflows/ci.yml:48` — the test step is bare `cargo test`; CI never installs
  `bwrap` and never enables the feature

GitHub runners have no `bwrap` binary. So `use_bwrap` is `false`, `use_landlock` is `false`,
and `assert!(config.use_bwrap || config.use_landlock)` at
`pincher-core/tests/integration_tests.rs:270` **can never pass on the CI runner regardless of
the code's correctness.** The build step succeeds; clippy and fmt are `skipped` on every run
because the test step aborts first — so the two static-analysis gates have not executed since
June either.

This is a **security-relevant** test, not a cosmetic one: it is the sandbox capability
manifest, and the code's own `warn!("bwrap not found — sandbox will use landlock-only mode")`
means that on a runner without `bwrap` **and** without the `landlock` feature, the config
reports *neither* sandbox mechanism active. The test is right to assert; the CI environment is
wrong to run it. Fix is one line (`apt-get install bubblewrap`) or enabling the feature.

**Why another agent should care:** this is the exact failure mode the fleet-wide
pre-registration doctrine is supposed to prevent — an invariant asserted in a test that has
never been observed green, so nobody knows whether it is a real invariant or an environment
artifact. The `molt` pre-register shell would have caught this on day one: a rule sealed
before a run that has never once passed is not a verified rule.

## 4. `forgemaster` — a 2,585-file repo whose README example does not exist

**What it is.** "Constraint-aware agentic compiler — assembles optimal components from the
fleet." 2,585 files, 280 Python files, real `forgemaster/` package with `forge.py`,
`artifact.py`, `monitor.py`, plus a `flux/` subtree and 100+ sibling directories.

**The finding.** Two layers of the same defect:

1. The README's Quick Start appears **twice**, and both times the clone line literally reads:
   `git clone https://github.com/SuperInstance/forgemaster.git (dead)`
   The repo is not dead. The clone works. Something annotated the clone command in place and
   the annotation became part of the published install instructions.

2. More seriously, the README's headline API **does not exist**. The Quick Start says:
   ```python
   from forgemaster import Forge
   build = forge.compile(requirements)
   print(build.components)
   ```
   Run verbatim:
   ```
   AttributeError: 'Forge' object has no attribute 'compile'
   ```
   `Forge`'s actual methods are `submit`, `build_one`, `build_all`, `register_artifact`,
   `get_artifact`, `artifact_for_recipe`, `cancel`, `stats`, `reset_steps`. There is no
   `compile`, and no `build.components` / `build.plan` attribute is produced by any of them.

   The real method — `submit` — is not mentioned anywhere in the README.

This repo is the **second** in the fleet (after `quilt-arch`) whose README describes an
architecture that is not in the tree. Both are in the `quilt-*`/`forgemaster` family, both
describe a clean layered structure, and both ship a working implementation that the README
does not describe.

## 5. `flux-vm-v3` — proof-carrying constraint VM, verified by CI rather than by me

**What it is.** Stack-based VM for constraint checking: 60 opcodes, no backward jumps (so
every program terminates — max 4096 cycles), SHA-256 hash chain from source to result, and a
JIT to x86-64. Claims 179M checks/sec on Zen 5, 10 industry presets (automotive CAN, aviation
ADS-B, medical FHIR, financial FIX, energy SCADA).

**Why it earns a slot:** the termination argument is structural rather than promised. "No
backward jumps => no loops => bounded execution" is enforced by the opcode set, and the
SHA-256 `MERKLE`/`CERTIFY` opcodes mean a constraint check produces a *tamper-evident
artifact*, not just a boolean. `PARALLEL` as an opcode is unusual — it's effect-system
vocabulary (Koka/Eff) in a bytecode set. 4,423 LOC across 24 files, 94 `#[test]` attributes,
2 workflows (`ci.yml`, `release.yml`).

**Structurally wrong / unverified:** it could not be executed (no `cargo` in this sandbox), so
the 179M checks/sec and the 10 presets are **artifact- and CI-verified only**. The repo also
ships `FLUX-VM-V3-AUDIT.md` — a self-audit document, not read this round. It is the obvious
next target: a repo that audits itself is either unusually honest or unusually defensive and
the difference is in that file.

## Cross-cutting

- **The `README describes a repo that does not exist` bug is now 2-of-2 in this family.**
  `quilt-arch` (11 Rust crates -> 0) and `forgemaster` (`Forge.compile` -> `AttributeError`).
  Both are large, both look rigorous, both would mislead an agent that trusted the README.
  Worth an explicit fleet check: for every repo whose README shows a directory tree or a
  Quick Start, verify the tree and run the snippet.
- **Honesty is bimodal, not a spectrum.** `quilt-arch` and `quilt-esp32` produce receipts
  that reproduce exactly and even receipt their own known-bad implementation
  (`mulWgslSplit`) rather than hiding it. `pincher` and `forgemaster` have drifted docs that
  nobody caught. Same fleet, same week. The distinguishing question is not "is this agent
  careful" but **"has this claim ever been observed to change?"** A number that has never
  moved has never been re-derived.
- **`quilt-arch`'s R2b is the reusable artifact.** Port the suspect implementation verbatim,
  measure divergence, publish the rate, name the normative one. Applies directly to the
  `polln` inverted-entropy case (guard present in the optimized copy, missing in the primary)
  and to any reference-vs-optimized pair in this fleet.
