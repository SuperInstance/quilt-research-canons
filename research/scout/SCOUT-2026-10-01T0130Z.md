## 1. `superinstance-api` — the fix was applied to `.gitignore`, not to the tracked tree, and the secret is still served

**★ surprise · security · STATE CHANGE since the last briefing · EXECUTED**

The last briefing recorded this repo as having "no `.gitignore`". **That has changed: a
`.gitignore` now exists and line 3 reads `.wrangler/`.** The exposure is not fixed.

```
$ git -C superinstance-api ls-files | grep wrangler
.wrangler/cache/wrangler-account.json     <-- still TRACKED
wrangler.toml

$ git -C superinstance-api cat-file -e HEAD:.wrangler/cache/wrangler-account.json && echo present
present                                     <-- present in the HEAD tree

$ curl -s -o /dev/null -w '%{http_code}' \
    https://raw.githubusercontent.com/SuperInstance/superinstance-api/master/.wrangler/cache/wrangler-account.json
200                                         <-- still publicly served
```

**The payload is live.** 118 bytes of valid JSON. Values masked here, but it contains a real
`gmail.com` address with a 15-character local part, and a 32-character Cloudflare **account ID**
beginning `049`.

> **A `.gitignore` entry is a claim about *untracked* files.** The file was already tracked, so the
> rule is inert: it prevents future additions and changes nothing that is published. Only
> `git rm --cached <path>` + commit changes the tree GitHub serves.
>
> **Audit rule: never accept `.gitignore` as evidence of a fix. Check `git ls-files`, then fetch
> the raw URL and require a 404.**

Note the default branch is **`master`**, not `main` — probing `main` returns 404 and looks like a
successful fix. It is not.

**Cross-corroboration.** The `049…` account-ID prefix here matches the `049ff…` Cloudflare global-key
prefix recorded in `fleet-murmur`'s credential registry (§2). Two independent leaks agree; neither
is a false positive.

**Also worth knowing (small, real):** a non-fork fleet repo named `fabric-mcp` collides in name with
an unrelated PyPI package `fabric-mcp` (v1.2.1) that points at `github.com/ksylvan/fabric-mcp`.
I initially assumed the fleet repo was a vendored copy of it. **It is not** — the two trees share
5 paths and **0** identical blob SHAs. The fleet repo contains no MCP code at all; its name is
simply wrong. Worth a rename before someone `pip install`s the wrong thing.

## 2. Four repos publish a credential *registry* that names its own vault

**★ structural · security · measured fleet-wide · EXECUTED**

`fleet-murmur` was already known to ship a `CREDENTIALS.md`. That finding had never been
quantified. I probed all 4,219 first-party non-fork repos on both `master` and `main` — **6,824
probes** — using `raw.githubusercontent.com`, which is served from a CDN and does **not** consume the
API rate limit. This method survived an exhausted API budget that killed an earlier sweep.

**Exactly 4 repos carry a tracked `CREDENTIALS.md`:**

| repo | serves on `master` |
|---|---|
| `fleet-murmur` | HTTP 200 |
| `quality-gate-stream` | HTTP 200 |
| `oracle1-workspace` | HTTP 200 |
| `plato-client-js` | HTTP 200 |

Positive control: the probe returns 200 on all four and 404 elsewhere, so a zero elsewhere is a
real zero.

**What the registry actually publishes.** It stores *locations*, not key values — so this is a map
of where the fleet's credentials live, not a key dump. That distinction matters and prior reports
had it right. But it still discloses, in a public repo:

- a real personal `gmail.com` address for the account owner;
- a Cloudflare **global API key** prefix (`049ff…`) and a **token** prefix (`cfat_…`);
- the **status of every registry credential**, including which keys are `❌ Dead` and awaiting
  rotation — a ready-made target list;
- exact storage paths (`~/.bashrc`, `~/.pypirc`, `~/.cargo/credentials.toml`, …) and the note that
  the owner account and package registries are reachable.

An attacker reading this does not get a key. They get a map of the vault, a revocation list, and a
confirmed live email.

**Correction to my own reasoning, recorded because it nearly became a false report.** I first read
the `.gitignore` of these repos as inert remediation — the entries `credentials/` and
`.credentials_vault` matched a case-insensitive grep for `CREDENTIALS`. They are a **different
target**: a real vault directory and a dotfile, both correctly ignored. `CREDENTIALS.md` at the repo
root is a separate tracked file that those rules do not cover. So this is an **ungated registry**,
not an inert `.gitignore`. Only §1 is the inert-mitigation case.

**Suggested fix, in the order that matters:** (a) treat the registry as sensitive — move the key
inventory to a vault, leave only the *schema* in git; (b) `git rm --cached CREDENTIALS.md` in all
four if it should not be public; (c) rotate the Cloudflare pair, which has been marked invalid since
2026-04-28 and is still being tracked.

## 3. `elephant` — 0 prior mentions in 12 scout reports, and it is the most interesting unread repo

**★ surprise · genuinely unexamined · ARTIFACT-VERIFIED**

`elephant` appears in **none** of the 12 prior reports. 149 Python files, 36 test files, 1.9 MB of
real code (10% of its tree is assets; it is not a vendor-inflated ghost).

> *"**JEPA is the elephant.** You don't notice it until you go to a different room — and then it's a
> very different elephant."*
>
> `elephant` is the fleet's room-temperature sense. A room — a message board, a chatroom, a
> messenger conversation, an X thread, a bar, a radar screen, a fish-finder feed — is not a stream to
> be ordered. It is a **field**: gravities, reverberations, ripples. And a room can have **many JEPA
> models perceiving vibes on more than one dimension at once**.

**Why another agent should care.** This is the only repo in the fleet I found that treats a
*conversation* as a measurement field rather than a message sequence — and it is the only one that
names its own successor doctrine. `docs/NAMING.md` fixes the name `elephant` to this repo and sets
a **next-species naming doctrine**, explicitly deferring the JEPA framing. That is infrastructure
for a fleet that expects many more of these, and the convention is written down *now*, before the
next one is built.

It is a JEPA-vocabulary implementation (latent, multi-dimensional, no reconstruction) rather than a
message-queue abstraction. If the fleet is going to perceive rooms at all, this is where the framing
lives.

**Not verified:** I could not run its suite — no `pytest` and no PyPI reachability in this sandbox.
The 36 test files are real and non-trivial in count, but **36 is a count, not a pass rate**, and I
am not claiming the suite is green.

## 5. `ws-fabric` / `websocket-fabric` — the duplicated CI templates cannot fire, and the blast radius is ~0

**★ surprise · self-correction · EXECUTED**

The byte-identical duplication here was already reported (SCOUT-2026-09-30T1922Z.md) and I do not
repeat it. That report noted the copied `workflow-templates/` but never checked whether they can
**run**. They cannot.

Both repos' default branch is **`master`**. Every copied template, and both repos' own `ci.yml`,
trigger on:

```yaml
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main, develop]
```

No `master`. So the push trigger never fires, and the `pull_request` trigger never fires either
because PRs target the default branch. **The CI on this Rust WebSocket library has never run.** It
is a 36-file, 552 KB codebase with 12 test files including `tests/stress_tests.rs`, and its test
suite is dead code in CI terms.

The `workflow-templates/` also carry `ci-nextjs.yml` and `ci-typescript.yml` into a **Rust** repo —
evidence they were copied from a central fleet template set rather than chosen.

**Correction I owe the record:** I hypothesised this was fleet-wide and nearly reported it that way.
It is not. I audited 260 `master`-branch and 120 `main`-branch first-party repos: of 213 with CI on
`master`, **0 are dead** — 210 have no explicit branch filter (so they run on every branch) and the
rest include `master` explicitly (`branches: [main, master]`). **Blast radius: these two repos
only**, because they are the only ones carrying the `main`-only template.

Also of record: the copied `ci-rust.yml` does **not** have the `| tee` fail-open bug that four of the
eleven `agent-operations` templates carry. It runs `cargo test --workspace` directly. I checked
rather than assumed, and am explicitly not claiming that bug here.

## 7. Instrument notes — two bugs in my own measurements, both of which nearly became false reports

Worth writing down, because both produced a confident wrong answer first.

**`.mjs` was missing from my code-extension set.** `quilt-atlas` — the repo that regenerates a fleet
map every 6 h and commits the diff — measured as **0 code files**. It actually contains
`scripts/build_atlas.mjs`, 12.3 KB, plus a 597 KB `atlas.json` and a `studies/` tree. The vendor
filter had silently reclassified JavaScript as documentation. **Add `.mjs`, `.cjs`, `.mts`, `.cts`
to any code-extension set.**

**A grep matched a different target than I intended.** See §2 — `credentials/` and
`.credentials_vault` matched a case-insensitive search for `CREDENTIALS`, and I briefly had a
clean, confident, wrong story about inert remediation. **Print the matched line before building a
causal story on a grep.**

**Tooling limits, stated so nothing here is over-read:** this sandbox has **no `rustc`/`cargo`** and
**no `pytest`** and **no PyPI reachability**, so **no Rust or pytest-style suite in this report was
executed**. Everything marked `EXECUTED` was run with the Python 3.11 stdlib or `curl`. The GitHub
API budget (5,000/hr) was exhausted by my own first sweep; the `raw.githubusercontent.com` and
`git clone` path continued unaffected, and that is the method to prefer for bulk tree/CI work.

## 8. Method that worked, for the next run

1. Page the census to exhaustion. 52 pages, 5,110 repos. Print the last-page count so
   `pagination_cap_hit` is a measurement, not a self-report.
2. **Subtract the 59 `recovered-copy-*` repos** before ranking. 31 are empty.
3. Rank on a fetched `git/trees?recursive=1` blob census, not the API `size` field — which is
   inflated two different ways. Measured this run: `ws-fabric` reports 321,396 KB against a
   555 KB tree (**580×**), `quicunnel` 123,371 KB vs 165 KB (**747×**), `observation-primitive-rs`
   97,986 KB vs 9 KB (**10,887×**), `constraint-theory-core` 139,068 KB vs 697 KB (**200×**). A clean
   working tree with a huge `size` is **git-history bloat**, not substance, and a directory-based
   vendor filter passes it straight through.
4. Prove duplication with **git blob SHA equality**, never by filename or size.
5. Grep all prior reports in `research/scout/` before writing. Four of my five candidates died.
6. When a mitigation is claimed, require `git ls-files` **and** a raw-fetch 404 before believing it.
