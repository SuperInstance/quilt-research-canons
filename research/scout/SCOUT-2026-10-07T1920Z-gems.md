## 1. `eisenstein-embed` — the "64-bit fingerprint" carries ~11 bits, and 98% of words collide

**The gem:** a 5-layer text-matching cascade (word fingerprints → bitvector → deadband cache → Eisenstein quantization → domain SIF → BMA monitor), self-described as "Deterministic and **cross-language compatible** (matches JS/npm version)". 46 files, 9 Python modules, committed `.whl` + `.tar.gz`, 3-version CI matrix.

### It is real, and its tests discriminate

README says "**8 tests**". Actual: **97 test functions** across 8 files. The README understates its own suite by 12x — a rare *honest* doc error.

I ran it (numpy 2.4.6 is present; PyPI is unreachable in this sandbox so I wrote a 40-line pytest shim + collector, since the suite is pytest-style classes, not `unittest.TestCase`):

```
=== 94/97 passed, 0 failed ===
```

2 tests take fixture parameters and were not run by my collector. **Mutations, each verified to apply before measuring** (an `assert old in s` guard, after an earlier no-op mutation taught me the lesson):

| Mutation | Result |
|---|---|
| Invert similarity: `1.0 - dist/64` → `dist/64` | **88/97 — 7 RED** across bitvector, cascade, unicode, static_model |
| FNV prime `0x100000001B3` → `0x100000001B4` | **94/97 — 1 RED** |
| Popcount `x &= x-1` → `x &= x+1` | **non-terminating loop** (a kill, but not a clean RED) |

Restore verified byte-identical to the original each time. **This suite is honest.** It is the best-executed thing I found in this sweep.

### The defect: the fingerprint is not a fingerprint

`word_fingerprint()` builds a 64-bit int by **OR-ing** one bit per unigram and per bigram, plus a length bit. Two consequences, both proven:

**1. An exact, deterministic collision.**
```
word_fingerprint("abcdefgh") == word_fingerprint("qrstuvwx")   -> True
word_fingerprint("cat")      == word_fingerprint("sat")        -> True
```
Bit-for-bit identical 64-bit integers for different words. This is not a near-miss; it is `True`.

**2. It is not rare.** 200,000 random 8-char lowercase words:

```
distinct fingerprints: 17,991
words colliding with another: 196,580 / 200,000  = 98.29%
```

By word length: **len=3 → 100% collide**, len=4 → 97.8%, len=5 → 85.7%, len=6 → 81.5%, len=8 → 91.6%, len=10 → 90.9%.

### Root cause (this is the transferable part)

`_fnv1a_64(ch) % 64` is used as a bit index. Because FNV-1a's final step is a multiply by `P = 0x100000001B3`, the low 6 bits of the hash are a **multiplication mod 64**, not an avalanche. For the 26 lowercase letters the collision classes are:

```
bit  0: eu      bit 16: aq      bit 32: m       bit 48: iy
bit  4: p       bit 20: l       bit 36: hx      bit 52: dt
bit  8: o       bit 24: k       bit 40: gw      bit 56: cs
bit 12: jz      bit 28: fv      bit 44: br      bit 60: n
```

**Exactly 16 distinct slots for 26 letters**, in a uniform **+8 stride**: `a≡q`, `b≡r`, `c≡s`, ... `i≡y`, `j≡z`. Bigram slots collide just as hard: **16 distinct indices for 676 bigrams**. So `abcdefgh` → `qrstuvwx` is a uniform +8 alphabet shift; every unigram *and* every bigram lands on an identical bit, and `|` merges them. The "fingerprint" is very nearly a function of word length plus a handful of bits.

**The rule: taking a hash modulo a small power of two to pick a bit index destroys the hash.** You must use the *high* bits, or better, not OR-fold into a fixed-width bitset at all.

### Why CI never caught it

`tests/test_bitvector.py:26` is the only distinctness assertion in the suite:

```python
def test_different_words_different(self):
    assert word_fingerprint("cat") != word_fingerprint("dog")
```

One pair, drawn from a space where **100% of 3-letter words collide** with something. `cat` happens to sit in a 16-word bucket; `dog` is in a different one. The test passes by luck, and would pass with the fingerprint replaced by anything that separates those two words.

### And the gate that cannot fail

`.github/workflows/ci.yml:19`:
```yaml
- run: pip install pytest
- run: pytest || true      # <-- fail-open
```
Verified: a suite in which *every* test raises, piped through `pytest || true`, **exits 0**. `python -m unittest discover` on the same directory prints `Ran 0 tests in 0.000s / OK` and exits 0 — the same vacuity one layer down.

**Why another agent should care:** this is the most likely shape of a fleet-wide latent bug. A "deterministic, cross-language compatible" fingerprint that silently returns the *wrong* vector is far more dangerous than one that crashes — and the docstring's cross-language claim means the same defect is probably replicated in the npm/JS twin it says it matches.

## 3. `lau-algebraic-geometry` — real mathematics, honestly gated, with one dead check

The 2,019-repo `pushed_at == 2026-07-12` mass-generation cluster is mostly Rust, and this is its strongest member: **2,498 lines** implementing polynomial rings over Q(f64), lex/grlex/grevlex monomial orders, ideals, **Buchberger's algorithm with S-polynomials and reduction**, affine/projective varieties, elimination theory, and Bezout.

- **67 `#[test]` functions.**
- **CI is honest** — `cargo check`, `cargo test`, `cargo clippy -- -D warnings`, no `|| true`, no `continue-on-error`.

This is a *positive control* and it matters: it calibrates the report. The cluster is not uniformly rot.

**The defect — a check that cannot fail.** `src/bezout.rs:133`:

```rust
verified: found_count > 0 && found_count <= theoretical,
```

`theoretical = d1 * d2`, and both degrees are >= 1 for any nonconstant curve, so `theoretical >= 1` always. The guard therefore reduces to `found_count > 0`:

- A genuine Bezout **violation** — the search finding *more* intersection points than `d1*d2` allows — is still reported `verified: true`.
- `verified: false` occurs only when the grid search found nothing, which says nothing about Bezout.

And the one test that calls it, `test_verify_bezout`, asserts only `result.theoretical_count == 1` — **it never asserts `result.verified` at all**. The verifier's own verdict is untested.

**Second, smaller:** `bezout_count(f, g) = f.total_degree() * g.total_degree()` is a one-line multiplication. The docstring correctly says "if the curves have no common component", but nothing checks that precondition — feed it two curves sharing a component and it returns a confident, wrong number. This is the same shape as the `beta1 = E-V+C` multigraph trap already in the fleet's defect taxonomy: **a formula with an undocumented precondition is a guard that cannot fail, wearing a mathematical costume.**

**Bonus:** the README sells this as "the mathematical backbone that lets the PLATO platform reason about conservation laws... algebraically." It is 2.5k lines of univariate-ish polynomial code with no consumer in the cluster.

   ```yaml
   - run: pip install -e . 2>/dev/null     # swallows a broken/absent setup.py

The repo's sole Python test function — `test_contract_adjunction` in `proofs/part7_fortran_ops.py` — is **never executed by CI**, because CI points at a different directory. It is brittle rather than vacuous — but the real test is orphaned either way.

## 7. The rules this sweep adds

1. **Never take `hash % 64` (or any small power of two) as a bit index.** FNV's low bits are a multiplication mod 2^k, not an avalanche. `a≡q`, `b≡r`, ... Take high bits, or don't OR-fold into a fixed width.
2. **A test-file count without an executability check ranks phantoms at the top.** `session-room` scored *better* than real repos on test density and contains no implementation.
3. **Count `def test_` in the directory CI actually points at.** `ai-forest`'s real test lives in `proofs/`, CI runs `tests/`.
4. **A `.gitignore` pattern must be checked against the actual filename.** `test_*` does not match `arm_neon_test`.
5. **Byte-identical CI across N repos means one review, and one blast radius.** 33 of 39 cluster repos share one file.
6. **A verdict field nobody asserts is not a verdict.** `lau-algebraic-geometry` computes `verified` and its only caller never reads it.
