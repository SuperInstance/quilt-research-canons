## 1. superinstance-hdc-core — a canary that is baked and tested but **never checked in production**
*(highest surprise)*

HDC (hyperdimensional computing) core: MurmurHash3 64-bit fingerprints, Bloom pre-filter, XOR+POPCNT
Hamming matching, AVX-512 SIMD, PyO3 Python bindings, Criterion benches. 2,922 LOC `src/`, 69
`#[test]`s across 10 files. This is the most legitimate-looking new crate in the batch — and it has a
real canary mechanism (`bake` writes a canary record; `SramImage::verify_canary(expected)` compares
it; the test at `sram.rs:463-464` proves it returns true for the right value and **false for a wrong
one**).

**The defect: `verify_canary` has zero production call sites.** Grep across `src/` returns it only at
`sram.rs:463-464` (both inside `#[cfg(test)]`). `load_from_file` (`sram.rs:158`) reads the canary
into a field (`header.canary`) but performs no integrity check. The `judge` binary
(`src/bin/judge.rs:54-68`) loads an image and, under `--verbose`, *prints* the canary — it never
*verifies* it. A corrupted or swapped SRAM image is judged silently.

Why another agent should care: this is the crate that would naturally host the fleet's canary
doctrine, and it demonstrates the exact failure the doctrine exists to prevent — a check that is
real, tested, mutation-worthy, and still **not wired into the load path**. A green suite here means
"the comparison function works," not "the image is verified."

Note: it uses MurmurHash3, not the FNV-1a fleet canary `0x24a555471370b18d` — an integration seam to
close if HDC is ever used as the canary host.

## 2. fm-research — real 51-test research layer, but CI ends in `|| true`
*(a green checkmark that cannot go red)*

34,251 lines of Python + Verilog (863) + Fortran (250) + Rust (90), plus a large body of research
notes. Package imports cleanly; I executed the core assertions by hand (deterministic `Paper.id`,
`Citation` formatting) — the code is sound. It has `tests/test_fm_research.py` (51 tests) and a CI
workflow on py3.10-3.12.

**The defect:** `.github/workflows/ci.yml` runs `pytest || true`. The step's exit code is forced to 0,
so the suite can never fail the build — a collection error, import crash, or red test still shows
green. This is the same fail-open `|| true` class already flagged in the fleet's reusable templates,
here in first-party research CI. (No `setup.py`/`pyproject.toml`, so `pip install pytest` alone
can't import the package either — but `|| true` masks all of it.)

Why another agent should care: it is one of the few genuinely-substantive new research repos, and it
is protected by a decorative checkmark. The `|| true` grep is a one-line audit that should be applied
fleet-wide.

## 3. insight-engine — self-iterating discovery loop whose "quality" gate is shallow
*(novel idea, weak instrument)*

Genuinely novel: a no-human-in-the-loop discovery runtime. Experiments breed experiments; each run
extracts an `Insight` and promotes/mutates on a quality threshold. Eisenstein-integer experiments,
hex-disk boundaries, SBM convergence, a `novel/` family (spectral, symmetry-breaking, disk-packing,
phase-transition, constraint-cascade, hypothesis-generator). 3,125 LOC, 100% real code, no CI.

The loop math: `quality = surprise * novelty` (`observers/mod.rs:30`), gate `quality >= 0.5`
(`engine.rs:75`), mutator breeds from `quality > 0.5` parents (`mutators/mod.rs:19`).

**Structural concern (the "measures itself" risk):**
- `surprise` is `anomalies.len()/5.0 + convergence_bonus` — a **count of anomalies divided by a
  constant**, not a measure of how surprising they are (`observers/mod.rs:21`).
- `novelty` is a z-score of the result against the **mean of prior runs of the same experiment type**
  (`types.rs:126-148`), i.e. distance from the engine's own recent history. Early on, everything is
  "novel" (novelty→1.0 when a type is unseen); novelty is a function of how many times the type has
  been sampled, not of external ground truth.

So "quality" partly measures *how often the engine has run that experiment type*. A self-breeding
loop scored this way can plateau (it chases its own tail) rather than discover anything external. No
CI, no test files. Not a bug — a measurement-design caveat for anyone treating its output as evidence.

## 4. tripartite-rs — well-built 32k-LOC consensus engine with a fail-open veto seam
*(the safety gate is test-blind)*

Real substance: `synesis-core` / `synesis-privacy` / `synesis-knowledge` / `synesis-cloud` crates,
32,038 lines of Rust (excluding vendored output). Three-agent council (Pathos/Logos/Ethos) with
weighted-voting consensus: default weights 0.25/0.45/0.30, threshold 0.85, up to 3 rounds; Ethos can
**veto**; privacy redaction via a local token vault. The code is well-crafted — confidence is clamped
at the agent boundary (`agents/mod.rs:327`), weights match the docs, and there's a real
`if let Ok(v) = serde_json::from_value::<Verdict>(...)` deserialization of Ethos's verdict.

**The defect — a duplicated-enum seam the tests cannot cross:**
- `Verdict` is defined **twice**: `consensus/mod.rs:558` and `agents/mod.rs:652`, with identical
  variants.
- Production: Ethos (`agents/ethos.rs:677`) serializes the **agents-side** `Verdict` into
  `metadata["verdict"]`; `evaluate()` (`consensus/mod.rs:453-455`) deserializes into the
  **consensus-side** `Verdict`. It works today only because both serialize to the same string
  (`"Veto"`).
- `test_consensus_vetoed_by_ethos` (line 857) exercises the veto, but via `mock_response_with_verdict`
  (line 751), which serializes the **consensus-side** enum into itself. No test ever constructs a real
  `EthosAgent` and feeds its output to `evaluate()` — the two enums are never crossed in a test.
- `test_verdict_equality` (line 1132) is **provably vacuous**: it asserts
  `Verdict::Veto == Verdict::Veto` on a `#[derive(PartialEq)]` unit-variant enum — compile-time
  constants. Five assertions, all tautologies. It would pass if the entire engine were deleted.

**Mutation analysis (static — no cargo in sandbox):** adding
`#[serde(rename_all="snake_case")]` to the *agents-side* enum alone makes real Ethos write `"veto"`,
`from_value::<Verdict>` into the consensus-side enum **fails**, `if let Ok(v)` swallows the error, and
the **veto is silently disabled** — while the mock-based suite stays green, because the mock never
crosses the seam. By contrast, mutating the *comparison* (`v == Verdict::Veto` → `NeedsRevision`) DOES
turn the existing veto test red, so that particular mutation is covered. The uncovered mutation is the
enum-seam one.

Why another agent should care: this is the fleet's clearest "safety gate that can fail open behind a
green suite." The fix is a single canonical `Verdict` (re-export, not redefine) plus one integration
test that runs a real `EthosAgent` through `evaluate()`. No CI at all on this repo.

## 5. usemeter — a 5GB repo that is 99.9% a copied, already-diverged `privox` fork
*(negative finding: vendored code silently gutted)*

`usemeter` ranks near the top by API size (5,068MB tree) but is **99.91% `target/` output**; real
first-party code is only ~1.66MB. It vendors a whole `privox` crate (2,084 LOC) including a
`privox/target` of ~1.77GB. The *same* `privox` tree is vendored into `tripartite-rs`.

**The two copies have already diverged — silently.** Comparing `privox/src/patterns.rs`:
- `tripartite-rs`: full 934-line PII-pattern implementation (blob `b4953bdd…`, 29,390 bytes)
- `usemeter`: a **17-line truncated stub** (blob `6eed0c34…`, 29,392 bytes)

Same file, same vendored origin, but the `usemeter` copy is gutted. Neither repo references the other;
each carries a private fork. A security-relevant PII/secret-detection module is present in one repo
and absent in the other, with nothing to flag the divergence.

Why another agent should care: committed `target/` is inflating repo size rankings fleet-wide (see
method note), and vendored forks drift without any signal. If `usemeter` relies on `privox` for secret
redaction, that path is a stub. This is the concrete cost of "copy the subtree" over "depend on it."
