## GEM 1 — `nexus-runtime` — the only fully mutation-verified artifact in this pass

**What it is:** a deterministic bytecode VM + multi-dimensional INCREMENTS trust engine + COBS
wire protocol + fleet orchestrator, for agent-authored control code on 50+ embedded boards.
32 core opcodes (+29 A2A). MIT. Deps: `numpy`, `pyserial` only.

**Why another agent should care:** this is the closest thing in the fleet to a *provable* execution
substrate — a validator, an assembler, a disassembler, and an executor, with a trust engine that
gates it. It is architecturally adjacent to the cell doctrine (deterministic opcodes, witness ->
trust, polyformal layers) and it is the only repo in this scout whose test suite was proven able to
fail.

**Verified, not claimed:**

```
$ python -m pytest          # respects pyproject testpaths = ["tests", "hardware"]
2559 passed in 5.55s
```

The README claims **2,287 passing tests**. Measured is **2,559** — the badge *understates* its own
suite. This is the opposite of the common failure in this fleet.

**Mutation evidence (a check that cannot fail is not a check):**

| mutation | result |
|---|---|
| `nexus/vm/executor.py` first `== 0` -> `!= 0` | **3 red** — `test_jz_taken`, `test_jnz_taken`, `test_cmp_zero_flag` |
| `nexus/trust/engine.py:105` trust-decay regression constant `0.5` -> `0.4` | **1 red** — `TestTrustDecay::test_decay_reduces_trust` |

The suite genuinely covers the control-flow semantics of the VM and the decay math of the trust
model. (A third mutation — disabling the trust-profile cascade delete — produced no replace and
was **not** counted as evidence.)

**Structurally wrong:** `pyproject.toml` declares
`Homepage = https://github.com/nexus-runtime/nexus-runtime` — a **different org**. The repo sits
under `SuperInstance` with `fork: false`, so it is an unattributed copy, not a tracked fork. The
`nexus-platform/Edge-Native` companion it points at is not in this fleet. Provenance is unclear;
that is a claim about the tree, not a defect in it.

## GEM 2 — `quilt-cell-bridges` — the migration story, broken at the last line of every script

**What it is:** 63 bridge scripts that read a pre-Quilt SuperInstance system and re-emit it as a
`.qzt` cell graph (cells + edges + metadata) renderable by 3-View Studio. Directly on-doctrine: it
is the cell model being applied retroactively to the fleet. MIT.

**Why another agent should care:** it is the only artifact in the fleet that *enumerates* the
pre-Quilt systems and pins each to a cell schema. It is a machine-readable index of the ecosystem.

**Structurally wrong — two independent defects:**

**(a) 44 of 63 bridges cannot run outside one developer's machine.** The output path is a
hardcoded absolute path, in two flavours:

```
23 x  "/workspace/bridges/<NAME>.qzt"
19 x  "/workspace/superinstance-website/bridges/<NAME>.qzt"
```

Clean-clone execution, bridges run from their own directory:

```
bridges executed OK : 9
bridges FAILED      : 54
.qzt produced       : 0
```

The 9 that "passed" produce nothing either. The failure is always the *final write* — the compute
completes and the bridge dies on the path:

```
File ".../agent_family_to_quilt.py", line 243, in main
    out.write_text(json.dumps(qzt, indent=2))
FileNotFoundError: [Errno 2] No such file or directory: '/workspace/bridges/agent_family_to_quilt.qzt'
```

Neutralizing the two roots to a writable dir:

```
OK    : 32        (was 9)
FAILED: 31
.qzt actually produced: 23
```

So the real state of the repo is **32 runnable bridges producing 23 graphs**, against a README that
claims 66 live bridges and a badge claiming 66. The count itself is wrong three ways: 63 scripts
exist, 116 `*_to_quilt.py` paths exist in the tree, and the README says 66.

**(b) One bridge ships red and aborts before doing its job.**
`beta_family_to_quilt.py` runs a self-test at import-time `__main__`:

```
$ python beta_family_to_quilt.py ; echo $?
Running tests...
  File "beta_family_to_quilt.py", line 467, in test_quilt_to_beta_tier
    assert quilt_to_beta_tier(feature, {"user_id": "other_user"}) is None
AssertionError
1
```

`1` — and **no `.qzt` is emitted**, because the failing test at line 551 aborts before `main()`
completes. This is a *real* check (it can fail, and it does), but it is shipped failing. The
failure is masked in aggregate because sibling bridges do print `All tests passed.` — so a fleet
sweep that greps for that string sees green.

## GEM 3 — `logtensor` — 88 green tests, none of which touch the flagship innovation

**What it is:** transformers reframed as guidance systems. HGT attention =
`softmax(<Q,K> + w*(Q^K) + N*Vc*lambda_dot)` — Clifford-algebra bivector coupling plus a
proportional-navigation homing term drawn from missile guidance. Plus tensor decompositions
(Tucker, TT, CP, Schur, SVD/QR) and a "RUBIK'S CUBE" permutation tensor.

**Verified:**

```
$ python -m pytest tests
88 passed in 44.26s
```

**Structurally wrong — the headline feature is untested.** The proportional-navigation guidance
term is `hgt.py:285`:

```python
return self.nav_constant * closing_vel * los_rate
```

Mutation — zero the entire homing term:

```python
return self.nav_constant * closing_vel * los_rate * 0.0   # MUTANT
```

```
88 passed in 39.66s        <-- ZERO red
```

Instrumenting the line to announce itself when executed:

```
GUIDANCE-TERM REACHED  ->  0 occurrences
```

and `grep -rn "guidance" tests/*.py` returns nothing. **The term is never executed by any test, and
no test references it.** The one mathematical claim the entire README is built on can be deleted
and the suite stays green. This is the fleet's cleanest instance of a suite that certifies
construction rather than behaviour.

**Secondary:** `PermutationTensorTransformer.__init__` eagerly materialises the dependency graph —
2,375,680 entries in a `defaultdict(set)` for a `(32,16,8,8,8)` tensor, **2.98 s per instance**.
It is the dominant cost of the 44 s suite. Verifying `_build_dependencies` costs 5s+ of the run.

## Method notes / limits

- Rust and CUDA repos (`cudaclaw`, `polln`, `polychora-temporal`, `constraint-theory-core`) were
  **inspected, not executed** — no cargo/rustc in this sandbox.
- The 1200-repo candidate pool is a **sound superset** for finding substantive trees, because
  `size` (git history) is always >= real tree size. Repos below the cut (top-1200 size < ~221 KB
  vs a 23 KB median) cannot hide a large tree, but a genuinely small-and-good repo below the cut
  would not be examined here.
- `llvm-project` is the single truncated tree (GitHub 60k-entry cap) and is a fork; excluded.
- Mutation testing was performed on **3** systems (nexus VM, nexus trust, logtensor HGT). Absence
  of a red result is reported as *untested*, not as *correct*.
