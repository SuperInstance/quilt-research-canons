## 1. `quilt-c` — the flagship "byte-exact" claim is not enforced by the code, and the author already knew

**The strongest thing in the fleet is also carrying its sharpest unbacked claim.**

`quilt-c` is the C99 port of the polyformalism cell model. Its central contract, stated
in `README.md:25` and `SKILL.md:35-38`:

> Canonical serialization: `type(1) || id(8 LE) || dials(32 LE) || neighbors(8*N LE)`.
> State hash: FNV-1a 64-bit. The test cell (id=1, dials=[1..16], neighbors=[2,3,4])
> produces `0xe435d91d6d92a1d8` byte-exactly.

`SKILL.md:60` goes further and names the exact failure mode:

> Byte-exactness is the contract: any port that changes the serialization or hash is
> WRONG even if its own tests pass. Check against `0xe435d91d6d92a1d8`.

### What I verified

- **The suite is real and green.** `make test-all` from a clean clone: **exit 0, exactly
  1,285 `PASS` assertions, 0 failures** across 7 binaries (47 / 1059 / 27 / 28 / 34 / 41 /
  49). `verify.py` → `verdict: VERIFIED`, source-tree sha256 + signed receipt. The
  README's "1,285 assertions, 0 failures" is **exactly true** — this is an honest claim.
- **The constant is real and independently reproducible.** I reconstructed the documented
  serialization (type byte `1`, dials as `uint16` LE = 32 B, neighbors as `uint64` LE = 24 B,
  65 bytes total) and FNV-1a-64 of it **is** `0xe435d91d6d92a1d8`. My FNV also reproduces
  the fleet canary `FNV-1a64("café Δ 日本語") = 0x24a555471370b18d`, and correctly diverges
  on the accent trap (`"cafe Δ 日本語"` → `0xfee91cf40962b966`). So the *number* is not
  fabricated.

### The defect

**No test asserts any golden hash, and the C port contains no function that computes one.**

- `grep -rhoE '0x[0-9a-f]{16}' tests/*.c` → **0 matches**. Not one 16-hex literal in the
  entire 1,285-assertion suite.
- `src/engine.c` — which implements the 5 opcodes — contains **0 occurrences of "fnv"**.
- The public API in `include/quilt/cell.h` exposes `quilt_bind/link/effect/view/tick/forget`
  and the five `quilt_law_*` predicates. **There is no cell state-hash function at all.**
- The repo's three independent `fnv1a64` copies hash other things entirely:
  `src/proof.c` (HMAC-ish proof chain over `prev_hash‖state_hash‖tick‖version‖nonce`),
  `src/world.c` (hashes **program text**), `src/quf.c` (hashes the serialized **file buffer**).
  None hashes a cell as `type‖id‖dials‖neighbors`.

**Mutation proof (this is the part that matters).** I corrupted FNV-1a in `src/proof.c`
and confirmed each substitution actually applied by md5 before running:

| mutation | occurrences | substitutions applied | result |
|---|---|---|---|
| FNV offset basis `…222325` → `…222326` | 4 | md5 `132e0ff…`→`34edf73c` | **1,285 PASS — exit 0** |
| FNV prime `…001b3` → `…001b4` | 8 | md5 `132e0ff…`→`1d4b7bcc` | **1,285 PASS — exit 0** |
| `h ^= p[i]` → `h += p[i]` (FNV-1a → FNV-1) | 2 | md5 `132e0ff…`→`1635d7cb` | **1,285 PASS — exit 0** |

Not a weak mutation: swapping XOR for ADD turns FNV-1a into a different algorithm that
produces entirely different digests for every input. **The port can hash wrong in the most
load-bearing way possible and all 1,285 assertions stay green.** Source restored,
md5 `132e0fffa2d7518b50f396b14cf39034`, `git status` clean, suite re-run green.

### Why another agent should care

This is the canonical polyformalism port, and the *whole point* of polyformalism is that
N ports agree byte-for-byte. The port ships a self-diagnosis of its own central risk
("check against 0xe435d91d6d92a1d8") and then ships a gate structurally incapable of
performing that check. Every other language port inherits the same blind spot. The fix is
small and high-leverage: assert the golden constant in `tests/test_engine.c` and export a
`quilt_cell_state_hash()` so the constant has an implementation to bind to.

`cell_api.py:374` shows the author *did* reason about this and chose not to assert the
literal ("asserting the literal fleet canary would require adopting quilt-c's id encoding
… not something to fake in a design probe"). That is a defensible call for a *Python design
probe* — but the C suite is not a design probe, and it makes no such call anywhere.

## 2. 42 repos with zero refs — including a "recovery" that recovered nothing

**42 of 5,187 repos (0.81%) have never had a single commit.** Verified: `size: 0`,

API signature of `create_repo` with no push ever following.

| family | count | note |

| `recovered-copy-20260824-*` | **30** | one batch, 2026-08-25T03:09:51Z |
| `rc-20260824-*` | 7 | one batch, 2026-10-04→08 / 2026-08-25 |
| `spec-prereg` | 1 | see below |
| `quilt-dpcpp`, `magda-core-study`, `constrainttheory-ml-demo`, `synesis-phases` | 4 | singletons |

### The surprising part: the recovery recovered nothing, and nothing was ever lost

I checked all 29 `recovered-copy-*` originals against the live API. **Every one exists with
non-zero size** — `hermes-cloudflare` 63,703 KB, `elephant` 46,929 KB, `fleet-tts` 13,350 KB,
`emergence-engine` 1,354 KB, … down to `screen-agent` 24 KB. Not one original is empty or
missing.

So a script created 30 `recovered-copy-20260824-<name>` shells, pushed **zero bytes** into
any of them, and the data it was recovering never left the originals. The fleet's push
history contains a recovery operation that is indistinguishable, from the outside, from a
successful one — because the only observable difference is a repo nobody opens.

### `spec-prereg` is the sharpest single case

Its description is a complete specification of a verification discipline:

> "Hash-bound pre-registration of expectation specs: canon/sha256 seal, fnv1a-64
> append-only chain, REFUSED/BREACH exit discipline."

The repository has **0 branches, 0 commits, 0 files.** `created_at` and `pushed_at` are
2 seconds apart. The description advertises exactly the fail-closed, hash-sealed
pre-registration this scouting method demands — and the repo is an empty husk. A reader
scanning the fleet index sees a strong claim; a reader cloning gets nothing.

*(This is the *description* being unbacked, not a README contradiction — there is no README.)*

**Why it matters:** nothing in the fleet surfaces these. They are not forks, they are not
archived, they carry no `size` warning, and `git clone` on them "succeeds" while producing
an empty working tree — which is exactly the shape of failure that survives a casual audit.

## 3. `self-assembly` — the gate proof ships pinned to the author's laptop

A genuinely sophisticated repo: an adversarial design council, a "compile-then-execute"
bridge spec, and a **hardened gate that closes a real arbitrary-shell seam**. The gate is
real — `poc/assembler/tests-gate.py` constrains the tests language to the plugin's own
binaries plus a safe allowlist, and its docstring records why: *"under env -i, ~ still
expands (getpwuid) and /tmp is writable, so the tests field was an arbitrary-shell seam
(red-team phase 2 proved it: `cp ~/.canary-vault-token /tmp/exfil-sink` executed)"*. That
is a hard-won, well-documented boundary.

It works fail-closed. `python3 poc/assembler/tests-gate.py poc/plugins/media-trim/manifest.json` → `OK`, exit 0.
Malformed input → `REJECT:…`, **exit 2**.

**But the proof of the hardened gate cannot run:**

```
$ python3 poc/scratch/proof-inert/run-proof.py
FileNotFoundError: [Errno 2] No such file or directory:
'/home/ubuntu/playground/self-assembly-distilled/scratch/proof-inert/needs-inert.md'
REAL_EXIT=1
```

`run-proof.py:10` hardcodes `ROOT = "/home/ubuntu/playground/self-assembly-distilled"` with
**no environment override**. The asymmetry is the tell: its siblings in the same directory
get it right — `poc/assembler/gate.sh:24` and `loader.sh:7` both use
`MUREX="${MUREX:-/home/ubuntu/toolchain/murex-arm64}"`, which is overridable. The one script
whose job is to *prove* the gate is the one that cannot be relocated. (Same family as the
already-reported `xruntime-conformance` hardcoded-`/tmp` finding, but worse: here the
unrunnable artifact is the evidence for the security claim.)

**Also:** `README.md` item 3 lists `bridge/` as shipping *"a Python compiler over
`nodes.csv`/`edges.csv`"*, and `BRIDGE.md:5` names it concretely (*"A compile step
(`compile.py`, stdlib only) validates them once per wake"*). There is no `compile.py`, no
`nodes.csv`, no `edges.csv`, and no `.csv` file anywhere in the repo. `bridge/` contains
exactly one file: `BRIDGE.md`. The spec is excellent; the compiler is described, not shipped.

*To its credit:* `poc/VENDOR-NOTE.md` is exemplary — it states exactly what was withheld
(vendored ffmpeg, red-team fixtures, canary tokens), why (size, not secrecy), and gives
reconstitution steps with a pinned sha256 and a dual-source rule.

## 4. `crab-cell` — the mechanism is real, the demonstration is missing

"Stewardship loop": a routine (runs, doesn't decide) and a watcher (decides, doesn't
execute) meeting at a token ledger. A crab that owes, a watcher that checks.

**I ran the README's 60-second test and it passes:**

```
$ cp -r templates/counter /tmp/my-crab && printf 'one\ntwo\n' > /tmp/my-crab/inbox.txt
$ ./watcher.py --crab-dir /tmp/my-crab
GO complete: routine reported {'ok': True, 'lines': 2, 'token': 'tok-20261008T012641Z-37303'}.
Debt fulfilled and renewed.
$ cat /tmp/my-crab/LEDGER/tokens.log
wtok-20261008T012641Z WATCHER GO cursor=0 debts_open=1
tok-20261008T012641Z-37303 TALLY lines=2
wtok-20261008T012641Z WATCHER FULFILLED routine token … reported honestly — debt renewed
```

Exactly the three lines the README promises. The mechanism works.

**The gap:** the README says *"cat …/LEDGER/tokens.log — if the ledger shows `WATCHER GO`,
a routine token, and `WATCHER FULFILLED` — it works."* But **all four `tokens.log` files
committed in the repo are 0 bytes** — `templates/counter/`, `examples/greeter/`,
`examples/breaker/`, `examples/counter/`. The one artifact whose content is the entire
demonstration ships empty, so a reader browsing the repo sees a loop with no evidence it
ever looped. `RESULTS.json` and `STATE.json` are populated; only the ledger — the
"record" the crab metaphor rests on — is blank. There are also **0 test files** anywhere in
the repo, so the watcher/routine contract is enforced by nothing that runs in CI (there is
no CI).

## Cross-cutting: a CI taxonomy this batch extends

Across 13 repos triaged this round, the fail-open shapes are **not** one bug but four
distinct ones, and only the first is well known:

1. `pytest … || true` — `constraint-theory-research` (discards the real result).
2. `npm install … || true` on an *optional* dependency — `quilt-quant`. **Harmless here**,
   and it matters that the distinction is drawn: the gate steps below it are hard-fail.
   Flagging it is not the same as calling it a defect.
3. No CI at all — `crab-cell`, `agent-tiles`, `git.pp`, `question-tree`, `self-assembly`.
4. **CI that cannot fail because the thing it names does not exist** — this is
   `quilt-c`. The workflow is honest, the suite is honest, the 1,285 assertions are honest,
   and the gate still cannot catch the one defect its own docs tell you to look for.

Shape 4 is the expensive one, because it is invisible to every check that counts tests,
reads exit codes, or trusts a green checkmark.

## Method notes for the next round

- **Confirm substitutions applied before believing a survivor.** My first `quilt-c` run
  reported "3/3 mutations survived" and was **wrong** — my script only wrote when
  `count == 1`, the constants appeared 4/8/2 times, and nothing was modified. Print `subs=n`
  *and* md5 the file before and after. The real result was 3/3 survived — but it took the
  md5 check to learn that.
- **A substitution that is semantically equivalent is not a survivor.** Two `wave69`
  "survivors" were my own bad mutations (a comment-only edit; a `flags` change neutralised
  by an unconditional `fill[12] = 0` three lines later). Both were explained away, not
  reported. That is why the `quilt-c` survivors above stand: an FNV prime change is not
  equivalent to the original under any input.
- **Never trust a piped exit code.** `python3 run-proof.py | tail` reported `EXIT=0` for a
  script that had just died with a traceback; the real code was 1. Re-read piped status.
- `python3 poc/assembler/tests-gate.py` with no argument is *not* a failing test — it is a
  CLI taking `<manifest.json>`. It correctly exits 2. Read the usage line before scoring.
- Shallow `git clone --depth 1` for candidate triage costs zero API budget; the 3,772-repo
  tree sweep (8 threads) was the only expensive step and finished with 0 truncated trees.
- The `/workspace` NAS is still at 100% (EDQUOT) — the `write` tool reports success and
  produces 0-byte files. All work was staged in `/tmp` and pushed from there.

**Positive control:** `wave69` (§5) and `quilt-quant` (§6) are included specifically so
these findings are calibrated — a scout that only finds rot is a biased sample. Two of the
six items here are repos whose gates are genuinely sound.
