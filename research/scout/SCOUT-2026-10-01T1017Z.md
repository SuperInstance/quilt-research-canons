## 1. `canary-3lang` — a documented NEGATIVE result, and the best methodological artifact in the fleet

**What it is.** The fleet canary ported to Futhark and BQN. Futhark **reproduces**.
BQN **does not**, and `BQN-FINDINGS.md` names all nine blockers.

**Why anyone should care.** This is the rare repo where the failure *is* the deliverable.
Eight of the nine BQN blockers "produce a plausible wrong number rather than an error,"
and it identifies which class each one is:

- BQN scalars are JS doubles, exact to 2^53. The canary is 2,640,610,520,279,855,501 —
  far past 2^53, so the literal silently rounds. *A 64-bit hash can be computed in limbs
  but cannot be named.* Verified: `(2^32-1)^2 = 18,446,744,065,119,617,025 > 2^53`, while
  `(2^16-1)^2 = 4,294,836,225 <= 2^53` — which is exactly why the port uses 16-bit limbs.
- `n | x` is mod with the divisor on the **LEFT** (`32 | 55` is 23) — backwards from every
  other substrate, and reading it the usual way is silently wrong.
- `÷` does not floor: `n ÷ base⋆3` returns `1.5e¯5` where the limb is `0`. **This one
  produced a visible `∞` further down the pipeline.**
- No hex literals; a trailing comment after a hex literal is absorbed into the digits.
- Any uppercase name is a function/modifier — a *role* error, not a binding error.
- A file may not begin with a comment: a comment-first file read through stdin produces
  silence and no error.

**Verified independently (no Futhark/BQN in sandbox — inspected, then re-executed the
algorithm):** `canary.fut`'s 18-byte literal is byte-identical to
`"café Δ 日本語".encode('utf-8')`, and re-running its exact algorithm (`xor64 h b * prime`,
u64 wrap, `0xcbf29ce484222325` / `0x100000001b3`) yields **0x24a555471370b18d = MATCH**.

**And it caught its own bug, in the most fleet-relevant way possible.** The source comment:
> "The implementation was correct throughout. What was wrong was a DECIMAL copy of the
> expected value pasted into a shell comparison: `0x024a555471370b18d` is
> 2640610520279855501, not 16314074854619246109. **A hardcoded constant nobody can
> re-derive is a test that lies.**"

That is the 17-digit/16-digit canary trap, documented from the inside by the agent that
hit it. It also flags the accent trap unprompted.

**Structurally wrong:** nothing found. The negative result is honestly labelled
("Futhark is verified. BQN is expected to be BLOCKED") and `run.sh` degrades honestly
rather than failing silently.

## 2. `quilt-fleet-tools` / `judge_gate` — the only instrument that verifies *the judge* before trusting the judge

**What it is.** Before an LLM judge's scores book as evidence, `judge_gate` runs two
probes: a **control pair** (same block, identical labels, twice → stability) and a
**label-shuffle null** (the same artifacts judged under swapped labels → the score must
not track the label). Every run writes a sealed, hash-chained receipt.

**Why anyone should care.** The whole JEV program scores things with models. `judge_gate`
is the missing epistemic precondition: *is this instrument calibrated at all?* An
independent judge and a biased judge are distinguishable in advance, by construction.

**Verified by execution** (`requests` stubbed on `PYTHONPATH`, network disabled):

| `label_bias` | verdict | mean_abs_diff |
|---|---|---|
| 0.0 | **PASS** | 0.0 |
| 1.0 | FAIL | 1.0 |
| 2.0 | FAIL | 2.0 |
| 3.0 | FAIL | 3.0 |

Independent PASSES, biased FAILS — the README's exact claim, confirmed. (A first attempt
appeared to show bias=0.9 passing with `mean_abs_diff` 0.0; that was **my** harness bug —
I passed `judge_messages()` dicts where `run_gate` expects transcript *strings*, so
`str(dict)` destroyed the transcript the mock hashes. Corrected input discriminates
perfectly. Recording it because it is exactly how a "the gate is broken" false positive
gets manufactured.)

`bench_seal` mutation-tested — **2 of 3 claims hold**:

- tamper a receipt's seal/hash → **RED, exit 1** ✅
- reorder chain entries → **RED, exit 1** ✅ (`seq expected N, got M — row spliced,
  dropped, or reordered`)
- **truncate the chain → GREEN, exit 0** ❌

The README says `verify` "detects tampering, reordering, **and truncation**." Truncating
`bench-seal.chain.jsonl` from 2 entries to 1 returns `{"ok": true, ...}`, exit 0.
**Root cause, `bench_seal/__init__.py:185-207`:** the verifier walks *forward* from
`ZERO` and judges each link independently, chaining from what is written
(`prev_expected = h`). There is **no expected-tip or expected-length anchor**, so dropping
the tail leaves every surviving link internally consistent. The inline docstring says
"detects tamper and reorder" — the *code* is honest; the README overreaches by one word.
**Fix:** pin the tip outside the chain file (committed, signed, or in a receipt the verifier
can't edit), then assert `entries[-1].entry_hash == anchored_tip`.

## 3. `quilt-arch` — the fleet's most rigorous conformance harness, with two real gaps

**What it is.** Q32 fixed-point kernels with **decision rules receipted BEFORE the runs**
— R1 determinism, R2 JS==Python cross-substrate, R3 conservation with an exact refusal
boundary, R4 journal inversion, R5 no-floats static scan.

**Verified by execution (pristine clone, `python3` available so R2 really crossed substrates):**

```
SMOKE OK        (3/3)
SMOKE ARCH OK   (27/27)      <- includes python ref selftest
smoke_chaos     12 PASS / 0 FAIL
E-A1 verdicts   R1..R5 all PASS, chain 10 links, tip 0x3ab0d64a76995315
```

R1 reports a **different-seed hash** (`e62c2c6b684181a4` vs `6f7e089887c401cb`) — a
constant-hash false-pass guard that is actually armed, not decorative. R2 records
`mismatches: 0, python_exit: 0`.

**Mutation-tested — and it splits, which is the interesting part:**

- Mutate `mulNorm` (`(a*b) >> SHIFT` → `>> (SHIFT+1n)`, the normative multiply R2 checks):
  `e_a1_conformance.mjs` correctly reports **R2: FAIL** — but **exits 0**.
- Mutate the boundary constant `LOG2_3` (`6806210843n` → `6806210844n`):
  `smoke_arch.mjs` → **exit 1** ✅, but `e_a1_conformance.mjs` → still **7/7 PASS**.

Two gaps, both structural:

1. **`e_a1_conformance.mjs` does not exit non-zero on a FAIL verdict.** It writes the FAIL
   into its receipt and returns 0. A check that cannot fail the build is not a check.
2. **CI never runs the conformance harness at all.** Both workflows invoke only
   `node smoke.mjs` (3 trivial checks: empty-string sha256, `randomBytes`, charter exists)
   plus the two smoke scripts. The 7-rule receipted harness with the hash chain is not in
   CI. Its correctness depends on a human remembering to run it.

Restoring both mutants returns 7/7 PASS with the **identical chain tip** — determinism confirmed.

**Positive note worth copying:** `quilt-arch` documents that the seed's `LOG2_3` constant
(6806210843) differs from true `log2(3)*2^32` (6807362106) and explicitly rules the
explicit constant normative — *"constants are canonical, not computed."* It receipted the
discrepancy instead of hiding it.

## 4. `erised-mirror` — README claims "75/75 across tools 01–10"; a clean clone produces 0

**The finding.** `README.md` advertises "Twelve tools... **75/75** across tools 01–10, plus
fleet rounds: mirror 6/6, trends 6/6" and "each tool runs in seconds." Description claims
"45/45 receipt chains verified... 6/6 green."

**Clean-clone sweep, all 15 entrypoints:**

```
exit 0 = 0,  nonzero = 15,  artifacts produced = 0
```

**Root cause:** `quilt-toolkit.mjs:22`

```js
import { QuiltEngine } from '/home/z/my-project/quilt-playtest/packages/core/dist/index.js';
```

A hardcoded absolute path into the author's home directory, plus a second at line 164
(`createRequire('/home/z/my-project/scripts/quilt-lab/package.json')`). There is **no
`package.json`** in the repo and the dependency is not vendored, so it is unrecoverable
without knowing the author's machine. Every tool fails at the final import; the compute
never starts.

**Why this is worse than an ordinary broken build:** the repo **commits `outputs/*.txt`**
— 13 pre-rendered result files from the author's machine. A reader sees real-looking
evidence that the tools work. This is the same class as the previously-found
hardcoded-absolute-path family in `quilt-cell-bridges`, and it is now 2 for 2 on the
"commits the output, can't reproduce the input" shape. **Grepping a repo for
"All tests passed" or for committed result artifacts measures the wrong thing entirely.**

**Also:** zero CI workflows, zero test files.

## 5. `quilt-jepa` — genuinely honest science, and a verifier that can never pass in a clone

**What it is.** A tiny JEPA world model in an anisotropic cell mesh, with pre-registered
sealed claims. **3/6 PASS** — and it publishes the three failures with root-cause analysis
rather than hiding them. Energy conserved to 1.2e-8 rel; determinism byte-exact.

**Verified:** `node run.mjs` → `{"P1_learning":false,"P2_ema_stationarity":true,
"P3_anomaly_surprise":false,"P4_determinism":true,"P5_diffusion_conservation":true,
"P6_zero_self_repair":false}` — matches the README's "3/6 PASS, with the full honest
analysis."

**Mutation-tested the chain — it is not vacuous.** Rewriting a payload at row 3 →
`FAIL hash mismatch at row 3 (P3_anomaly_surprise#3)`, exit 1. Re-verify restored → 7-row
chain, tip matches, 0 failures. The hash chain is sound.

**The defect: the mtime binding is unverifiable in every future clone.**

```
sealed mtime_local_ms : 1790574965122  (2026-09-28T05:56:05Z)
clone  mtime_ms      : 1790850174057  (2026-10-01T10:22:54Z)
delta                : 275,208,935 ms ≈ 3.2 days   (tolerance: 2000 ms)
FAIL registration mtime binding — exit 1
```

`git clone` sets mtime to clone time, so `Math.abs(st.mtimeMs - seal.mtime_local_ms) > 2000`
**can never be satisfied outside the working tree that sealed it.** `verify.mjs` is
fail-closed and honest — but it is permanently red for every future auditor, including CI.
The README advertises `verify.mjs — "exit 0 only if everything re-hashes."` In practice it
never exits 0 again. **Fix:** bind content, not filesystem metadata — hash the stripped
registration body (already done via masked self-sha) and drop the mtime clause, or store
the mtime as evidence and never gate on it.
