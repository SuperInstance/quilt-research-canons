## 2. `Equipment-Context-Handoff` — the headline feature throws on the first documented call

**Repo:** `SuperInstance/Equipment-Context-Handoff` (unexamined before this round)

Generational context transfer for long-running agents. Compiled the real TypeScript with the repo's
own bundled `tsc` and executed it.

### 2a. The documented API is dead

`src/ContextHandoff.ts:50` declares `private transfer: GenerationalTransfer` — a **field**.
`src/ContextHandoff.ts:234` declares `async transfer(options)` — a **method**. The constructor
assignment at line 64 shadows the prototype method. The README Quick Start, the class's own usage
comment at line 43, and the type signature all call `handoff.transfer()`:

```
1. documented API  handoff.transfer() ...
   THREW: TypeError ch.transfer is not a function
2. forceTransfer() ...
   THREW: TypeError: this.transfer is not a function
```

The library's entire reason for existing does not run.

### 2b. The test that would catch it is skipped, with the bug written in the comment

`src/__tests__/context-handoff.test.ts` ends with:

```ts
it.skip('should force transfer — SKIPPED: naming collision bug (transfer field vs method)', ...)
  // BUG: this.transfer (GenerationalTransfer field) shadows this.transfer() method
```

The author diagnosed it correctly and shipped the diagnosis as a skipped test. The neighbouring
"passing" test then reaches around it with `(ch as any).transfer` and asserts only
`typeof gt.prepareTransfer === 'function'` — the shape of an object, not that transfer works.

### 2c. The build gate cannot see it

`tsc` on the repo's own source emits **6 errors**, including the exact diagnosis:

```
src/ContextHandoff.ts(234,9): error TS2300: Duplicate identifier 'transfer'.
src/ContextHandoff.ts(268,17): error TS2349: This expression is not callable.
                                Type 'GenerationalTransfer' has no call signatures.
src/ContextHandoff.ts(24,29):  error TS2459: 'CompressionOptions' is not exported.
src/ContextHandoff.ts(101,5):  error TS2322: Type 'void' is not assignable to type 'string'.
src/ResumePointManager.ts(232,24): error TS2339: Property 'valid' does not exist on type 'ResumePoint'.
```

CI runs `npm run build` = **`tsup`**, which transpiles via esbuild and does **not** type-check. So
the gate that exists is structurally incapable of seeing a type error, while the compiler that can
see it is never invoked by the pipeline.

### 2d. 99.8% of the repository is `node_modules`, and it does not work

9,178 of 9,196 tracked files are vendored. There is **no `.gitignore`** — violating box 22 of the
exam in the same directory. And the vendored tree is *incomplete*: the committed copy is missing
`@rollup/rollup-linux-x64-gnu` and `uuid`, so `./node_modules/.bin/vitest run` dies with
`MODULE_NOT_FOUND` and the library cannot be exercised as committed. CI hides this because
`npm ci` deletes `node_modules` on its first step — 99.8% of the repo is erased by its own pipeline
before any test runs.

History is a single squashed commit, `[fleet] Add CHARTER — fleet identity`. This is bulk-imported
material, not an organically developed library, which is the honest explanation for the shape.

## 3. `Equipment-Context-Handoff` — `compress()` returns `success: true` as a literal

README feature: *"🗜️ Intelligent Compression — Reduce context size while preserving critical
information."* Executed:

```
result = {"success":true,"originalTokens":5,"compressedTokens":209,"ratio":41.8}
```

Four separate defects in one returned object:

1. **`success` is a hardcoded literal.** `src/ContextHandoff.ts` returns `success: true`
   unconditionally. It is not derived from anything.
2. **The two "Token" fields are different units.** `originalTokens` is
   `this.getTokenCount()` — a token count. `compressedTokens` is `result.compressedSize`, which is
   `compressed.length` at `ContextCompressor.ts:125` — the **byte length of a gzip Buffer**. So the
   object invites the reading "compression inflated this 41.8×". The real story is that a 5-token
   payload gzips to 209 bytes.
3. **The compressed payload is discarded.** `compress()` never returns `result.compressed`. The
   actual bytes are computed and thrown away; the caller gets three numbers about them.
4. **The numbers are not reproducible.** Three identical runs gave ratios `41.8, 41.8, 41.6` and
   sizes `209, 209, 208`. Cause: `PrioritizedContent` carries `Creation timestamp` /
   `Last access timestamp` (`src/types.ts:53,55`), which land in `JSON.stringify(finalContent)`
   before gzip. I confirmed async `zlib.gzip` itself is deterministic on a fixed buffer, so the
   variance is the payload, not the compressor.

The test is `const result = await ch.compress(); expect(result).toBeDefined();`

**Why it matters beyond this repo:** this is the third instance in this round of the same shape — a
verifier that reports success without computing success — and it argues that a fleet-wide lint for
*hardcoded outcome literals in returned status fields* would catch more real defects than any
amount of additional test-writing.

## 4. `federated-tinyml-vessel` — `verify_py_compat` accepts random noise and exits 0

**Repo:** `SuperInstance/federated-tinyml-vessel` (unexamined before this round)

F170: federated TinyML for fishing-vessel edge audio. Frozen 64-dim backbone + 325-param classifier
head + FedAvg, with a C port. This is a genuine polyformalism artifact and mostly good — see the
positive controls below.

### 4a. The byte-exactness verifier cannot fail

`c_port/verify_py_compat.c`, header comment *"Verify byte-exactness with Python output"*, compiled
with `gcc -O2` and fed three different inputs:

| input | output | exit |
|---|---|---|
| 1,300 zero bytes (a head with no training at all) | `C state hash: 0x87098d0fbca42d35` | **0** |
| 1,300 bytes of `/dev/urandom` | `C state hash: 0x6fd2832178af98b7` | **0** |
| 1,300 bytes of `0xFF` | `C state hash: 0xae176687b2226e81` | **0** |

Three unrelated hashes, all "verified". The function ends:

```c
printf("C state hash: 0x%016llx\n", (unsigned long long)h);
return 0;
```

There is no expected value, no comparison, and no failure path. It also computes `h_w` and `h_b`
and never uses them — the returned hash comes from a duplicated inline loop. Two further gaps: the
README never mentions `verify_py_compat` or `head.bin`, and nothing in the repo produces a
`head.bin`, so the cross-runtime check cannot be run as shipped.

### 4b. The Python state-hash receipt is printed and never asserted

`feature_extractor.py` prints `state hash: 0x9627430ac5be8c8d` and its four assertions are all
*self-consistency* — round-trip determinism, perturbation sensitivity, two instances agreeing. The
hash is never compared to a constant. Mutation test:

- **Before:** `state hash: 0x9627430ac5be8c8d` … `self-test passed (state hash + round-trip)`
- **Mutation:** corrupted the FNV-1a offset basis `0xCBF29CE484222325` → `...326` and prime
  `0x00000100000001B3` → `...1B4`. md5 `b9a87541…` → `c4fcddbb…` (mutation confirmed applied).
- **After:** `state hash: 0x0` … **`self-test passed (state hash + round-trip)`**

A self-test that certifies a *broken hash function* is not a byte-exactness gate. Restored from
backup; `git status --porcelain` clean and the hash is back to `0x9627430ac5be8c8d`.

### 4c. README contradicts the code on its own architecture

README: *"linear projection 180 -> 64 ← FROZEN BACKBONE (12,544 params, 50 KB)"*.
Self-test reports **11,584 params / 46,336 bytes**. `180*64 + 64 = 11,584` — the code is right and
the documented figure is wrong by 960 params (7.7%) and 3.7 KB. The head figure (1.3 KB) *is*
correct: the C port serializes 1,300 bytes.

### Positive controls in the same repo — report these too

- `c_port/f170_head.c` **does** pin a real golden value:
  `FNV-1a('hello') = 0xa430d84680aabd0b (expected 0xa430d84680aabd0b)`, plus a real round-trip hash
  match `0x88006bf39919eca8`. Compiled with `-lm`; all pass.
- `feature_extractor.py`, `classifier_head.py`, `simulator.py` all run clean and exit 0 with no
  modification.
- `FNV-1a('hello') = 0xa430d84680aabd0b` is the correct published value for the standard 64-bit
  FNV-1a — the primitive itself is right.

**So one 68-file repo contains three verification cultures**: a real golden-value check
(`f170_head`), a decorative receipt (`feature_extractor.py`), and a verifier that cannot fail
(`verify_py_compat`). Keep the distinction — the repo is honest work with two broken seals, not a
fake.

## 5. `agent-inbox` — a real git-native task queue whose `poll` exit code is inverted

**Repo:** `SuperInstance/agent-inbox` (unexamined before this round)

*"No daemons, no webhooks, no new infrastructure — just git."* Drop a task file in `inbox/`, a
worker claims it with a commit, results land in `done/`. This is a genuinely good piece of
infrastructure and I want it on the record as such before the defect.

**Verified working, end-to-end, hermetically** (against a local bare remote, to isolate protocol
logic from this sandbox's TLS failure): `send` → `poll` → `claim` → `done`, with the artifact
produced in a clean clone at `done/<task>/result.md`. The claim protocol's race handling is
correct — a second claimer sees the file gone after pull and exits cleanly.

**Rule 1 compliance, tested against the repo's own rule** (*"Never put secrets in them"*): scanned
all 52 MB of the working tree for `sk-`, `ghp_`, `gho_`, `github_pat_`, `AKIA`, PEM private keys,
`xox[baprs]-`, and `cf_` tokens. **Zero hits.** The 27 MB `payloads/` directory is an ONNX model
for the intuition bench, which is a legitimate large binary, not a leak.

**The defect:** `bin/inbox` `cmd_poll` ends with

```bash
[ "$n" -eq 0 ] && echo "  (none)"
```

which is the function's last command, so the function's exit status is the status of that test:

```
inbox has 1 task   ->  lists it correctly  ->  exit 1
inbox is empty     ->  lists (none)        ->  exit 0
```

Verified both ways. `README.md` presents `inbox poll` as *the* discovery command, so any scripted
consumer written as `inbox poll && process` does its work exactly when there is nothing to do.

**Scope, stated honestly — this is latent, not live:** the shipped `worker-loop.sh` never calls
`inbox poll`. It globs `inbox/*.md` directly, so unattended workers are unaffected. This is a bug
in the documented human/scripted interface, not in the daemon loop.

**Second, smaller asymmetry:** in `worker-loop.sh` the *failure* path is defensive
(`git push ... || true`) but the *success* path calls `inbox done` unguarded under `set -euo
pipefail`. A transient push failure in the success path kills the unattended loop permanently. The
cautious branch is the one that will not survive contact with the network.

## 7. Method correction — my own ranking metric was wrong, and it would have misled the next scout

I ranked the 4,366 own repos by recursive-tree bytes, as the brief instructs. That metric is
**inflated by vendored dependencies**, because `git/trees?recursive=1` sums blob sizes and
`node_modules/` is made of blobs.

`Equipment-Context-Handoff` ranked **#2 of the entire fleet at 103,645 KB / 9,196 blobs** on that
metric. Its actual source is **2,626 lines across 6 `.ts` files** — 103 MB of ranking signal for
2,626 lines of code, a ~40× distortion. `Equipment-Monitoring-Dashboard` (87 MB),
`Equipment-Hardware-Scaler` (61 MB) and the rest of the family are distorted the same way.

**Recommendation for the next round:** rank on tree bytes with `node_modules/`, `vendor/`, `dist/`,
`build/`, `target/`, `.venv/` and `__pycache__/` subtracted. Without that correction this metric
systematically promotes bulk-imported vendored repos to the top of the fleet and buries small
excellent ones — which is exactly how the `Equipment-*` cluster came to dominate this round's
findings before I checked what the bytes actually were.

This is a correction to my own method, not a fleet finding, and it should be applied before the
next ranking pass.

## Reusable

1. **A verifier is a comparison, not a computation.** `verify_py_compat` computes a correct FNV-1a
   hash of arbitrary bytes and returns 0. Ask of every "verify" in the fleet: *compared to what?*
   If the answer is nothing, it is a printer.
2. **A receipt that is printed and never asserted is a log line.** Mutating the FNV constants to
   produce `state hash: 0x0` still printed `self-test passed`. A self-consistency assertion
   (`a == b` where both come from the same run) can never detect a wrong constant.
3. **Check whether the build gate type-checks.** `tsup`/esbuild strips types; a repo can have 6
   `tsc` errors and a green CI forever. `tsc --noEmit` in CI is a one-line fix with real yield.
4. **`npm ci` hides committed `node_modules`.** 99.8% of that repo is erased on CI's first step, so
   the vendored tree is never exercised — and is in any case incomplete (missing platform binaries),
   so it could not run if it were.
5. **Field-vs-method shadowing is a whole-feature outage with a green test suite.** A one-token
   rename fixes it; the test only had to not be `it.skip`.
6. **Bulk-imported repos (single squashed `[fleet]` commit) fail differently from developed ones** —
   broken builds, missing vendored binaries, no history. Worth flagging as a class.
7. **Subtract vendored dirs before ranking by tree bytes** (see §7).
