## 0. The census itself was wrong before this run (method note)

Two things in the standing brief are stale, and both would have produced a bad census:

- **"`claw` (6,089 TS files) is the largest repo."** `claw` is `fork=true` — it is a
  fork, not fleet-authored. So is **`MicroMoth-quilt`** (the brief's research-engine
  exemplar). A `fork==false` filter — the obvious way to cut noise — **hides both**.
  I nearly reported a census that excluded the two repos I was explicitly told to read.
- **Stopping at page 1 is a 49x error, not 4x.** The account has **4,892 repos across
  49 pages** (Link header `rel="last"` -> page 49). 816 forks, 83 archived, 51 empty ->
  **3,956 substantive**.

**`sort=pushed&direction=desc` is NOT monotonic on this endpoint.** Page 1 interleaves
2026-09-15, 2026-08-31, 2026-09-03, 2026-09-30. Consequence: paging by push-date
**overlaps itself** — my first pass returned 4,892 rows containing only 4,119 unique
names, a silent 773-repo duplication. Re-fetching in a stable order
(`sort=full_name&direction=asc`) returned exactly 4,892 unique.

> **Standing rule, now enforced:** page via `sort=full_name&direction=asc`, and assert
> `unique_by(.full_name) == rows_returned`. If those disagree you are reading an
> overlapping page set, not a census.

`quilt-atlas` independently agrees: its `atlas.json` reports `total_repos: 4891`,
`pages_fetched: 49`, `pagination_cap_hit: false` (its count is 1 lower — a repo pushed
mid-run). Two unrelated methods converging on ~4,891 is the strongest evidence here.

## 2. `quilt-gpu-lab` — the receipt layer that caught its own bug (VERIFIED, MUTATION-TESTED)

**What:** standing ML experiment loop on an RTX 4050. 118 experiment scripts, 2,976-line

**Why:** this is the reference implementation of the fleet's *receipt* doctrine, and I
verified the receipt layer actually fails when it should.

- `python tools/receipt_manifest.py` re-seals `RESULTS.md` + `QUEUE.md` + 118
  experiment files + 18 tool/weight files into `receipts/manifest.json` (sha256).
- `python -m unittest discover -s tests` -> **6 tests, OK**.
- **Mutation test (the part that matters):** I appended one HTML comment to
  `RESULTS.md`. The suite went **RED** with a precise diff
  (`58f9d1dc...` vs `6829867a...`). Restored -> green. *A control that cannot fail is
  not a control; this one can.*

**The genuinely interesting find** — `receipts/manifest-repair-2026-09-30-d23b.md`
documents a **phantom seal**: the manifest pinned `d23b...=80e545bb...` while the
committed file hashes `a0a204fe...`. Autopsy: `80e545bb` matches **no committed
revision**; it entered at `fc79ff1` and was carried forward by `d5e7009`. Diagnosis:
**dirty-tree seal** — the manifest hashed working-tree bytes git never saw.

This is the best negative-result artifact in the fleet. The pin caught its own
mis-transcription on a clean clone, and the fix was a manifest regen with **no source
files touched**. Its own follow-up candidate is the right one: teach the sealer
`--require-clean`, converting *pin-caught-after-the-fact* into *refused-at-seal-time*.

**Structurally wrong:** no CI (`.github/workflows` absent) — a self-verifying receipt
suite that only runs when someone remembers. Its CI status is `workflows: []` in

## 7. Cross-cutting: the canary is 1-of-10, and its own text form is inconsistent

Of 10 repos cloned: `observation-primitive-rs` carries the canary; the other 9 do not —
including `constraint-theory-core`, `eisenstein`, `quality-gate-stream`, `quilt-gpu-lab`,
`sunset-ecosystem`.

I re-derived the canary from scratch (FNV-1a 64, UTF-8 bytes, offset basis
`0xcbf29ce484222325`, prime `0x100000001b3`):

```
FNV-1a 64("cafe" with accents: café Δ 日本語) = 0x24a555471370b18d   (62 bits, integer-verified)
```

**The integer is correct.** But the *string* is written two ways across the fleet —
3 occurrences of the 17-digit `0x024a555471370b18d`, 2 of the correct 16-digit
`0x24a555471370b18d`. The 17-digit form is not representable in 64 bits; a repo
string-comparing the padded form against a correctly-formatted canary will fail for a
reason that has nothing to do with the hash. **Compare the integer, never the text.**

## 8. `constraint-theory-core` — real crate, and its headline claim is false (MIXED)

**What:** `cargo add constraint-theory-core`. Zero dependencies, 229 `#[test]`
attributes, 10 src modules, published on crates.io with docs.rs. **Genuinely real
engineering** — the best-structured Rust I examined.

**But the README's central claim does not survive inspection.** It says snapping maps
continuous vectors to "exact Pythagorean coordinates... so a direction is defined by
**integers, not floats**." The implementation
(`src/quantizer.rs:413 snap_to_pythagorean`) returns **`f64`**, from a **hardcoded
16-entry table**. Checked with exact rational arithmetic:

- **12 of 15 rational entries are not exact in f64.** `0.6`, `0.8`, `5/13`, `12/13`,
  `8/17`, `15/17`, `7/25`, `24/25`, `20/29`, `21/29`, `9/41`, `40/41` are all f64
  approximations of the ratios they claim to be. Only `0.0`, `1.0`, `0.5` are exact.
- **The 16th entry, `sqrt(2)/2`, is not a Pythagorean ratio at all** — it is
  irrational, and any `a/c` with `a²+b²=c²` is necessarily rational. It sits in a
  table commented "Common Pythagorean ratios."

So the crate whose purpose is eliminating float drift **returns floats**, and its
lookup table is where a caller would expect exactness. The crate is worth adopting;
the README's "integers, not floats" line is not worth repeating. (Could not execute:
no `cargo`/`rustc` in this sandbox — this is source inspection plus an independent
Python re-derivation, and I did not run its 229 tests.)
