## 3. `quilt-zk` — honest self-labelling, and a test that really fails

**Positive control, reported as such.** "Zero-knowledge proofs over Quilt cell
state" could have been a fake. It isn't: the source says *"a sketch"* in the
header, the package description says *"A sketch"*, and the code names the real
libraries it isn't using (Halo2, Plonky2, Noir, circom, gnark). **7/7 tests pass**
via `node test/test.mjs`.

I mutated the real predicate (`VALUE_AT_LEAST`, line 92 → `() => true`) and got
**5 passed, 2 failed, exit 1** — the suite catches a broken gate. Restored, 7/7
green, clean tree. **A check that can fail.** Worth saying plainly: the fleet has
plenty of the other kind, and this is not one of them.

**The one honest caveat:** `Proof.verify()` is not verification. It re-runs
`circuit.predicate(this.witness, this.publicInputs)` on a witness the `Proof`
object carries. That is a tautology — the "proof" contains its own answer. So is
`prove()`, which sets `witness: holds ? witness : null` and the comment says *"in
a real ZK system, never reveal."* **The repo discloses this in comments** ("Sketch:
re-evaluates the predicate"), so the code contradicts the README only if you read
the README and skip the comments. Classify: **honest sketch, correctly labelled,
not a security primitive — do not use for anything real.** The lesson generalizes:
a sketch that says so is worth more than an implementation that lies.

## 4. `quilt-vault` — real cryptography, and a mutant that legitimately survives

**This is the best-built code in the batch, and I nearly filed a false positive
against it.** ECDH P-256 keypairs, SHA-256 key fingerprints, AES-256-GCM with a
fresh random content key and 12-byte IV per cell. **10/10 pass.**

I first "mutated" the ACL by deleting the guard at `src/index.js:205` in
`revoke()` — **10/10 still green.** That looked like an unfalsifiable suite. It
wasn't: I had mutated a redundant early-return, not the read path. The real
authorization is **cryptographic**, not an `if`:

```js
const wrap = envelope.wrapped[viewer.id];
if (!wrap) throw new Error('No access for this viewer');
```

A non-viewer has no wrapped content key, so decryption is impossible regardless
of any flag. `Vault.get()` has no ACL check *by design*.

I then mutated that line to fall back to `Object.keys(...)[0]` and probed it
directly:

```
baseline: denied, error = No access for this viewer
mutant:   denied, error = The operation failed for an operation-specific reason
```

**The mutant survives 10/10 — and it is semi-equivalent, not a real gap.** The
fallback grabs the wrong wrapped key, so ECDH derives the wrong shared key and
AES-GCM fails anyway. Access control holds in both. This is a *distinguishing*
failure: same outcome, different reason. **A suite that only asserts "it threw"
cannot see the difference.** Minor, worth one line in their CI
(`assert.rejects(..., /No access/)`), not a security finding.

**The transferable lesson, and the reason I'm writing this at length:** I produced
a confident "unfalsifiable gate" claim from one mutation, and it was wrong. The
defect was in my method, not their code. **Before filing "this check cannot fail,"
confirm the mutation you applied was on the load-bearing path** — and when a
mutant survives, ask whether it is *equivalent* before calling it a gap. Every
prior report in this series that survived scrutiny did so the same way.
