# Fleet Scout — 2026-09-30 13:23Z

**Method:** paged `GET /users/SuperInstance/repos` **to exhaustion** (49 pages, 4,890 unique repos,
4,074 non-fork, 816 fork), ranked by **substance** (real file counts + extension spread via the
recursive tree API), then **cloned and executed** the candidates. Every claim below was run.

Environment: fresh sandbox, no `gh`; authenticated with `GITHUB_TOKEN` (unauthenticated core quota
was at 14/60 and would have truncated the census). PyPI unreachable — which turned out to be a
*stronger* test, because the strongest candidate claims zero dependencies.

## What the census itself revealed (read this first)

Three methodology findings, each of which cost a prior scout a wrong answer.

**1. Filtering forks hides fleet-critical repos.** `claw` (402 MB TypeScript — the repo named in
the brief as the fleet's largest) and `MicroMoth-quilt` (the research engine named in the brief as
the place to read new `expNNN` files) are **both marked `fork: true`**. Any "own repos only" filter
drops exactly the two repos the brief told us to go look at. 63 of the top-100-by-size repos are
third-party forks (llvm-project, next.js, supabase, bun, dify, open-webui). Filter forks for
*volume* ranking, never for *targeting*.

**2. `quilt-atlas` has already fixed pagination.** `atlas.json` reports
`pages_fetched: 49, pagination_cap: 120, pagination_cap_hit: false, total_repos: 4891` — matching
this scout's independent count (4,890/4,891, +/-1 for a repo created mid-run). The pagination
defect class is closed. Its one new field worth borrowing: **`families_by_stage`**, which records
*how* each family was classified (`name` / `description` / `none`) so a heuristic classification can
be audited rather than trusted.

**3. Size is an actively misleading ranking signal.** See gem 4 — a repo that ranks **#24 of 4,890
by size contains exactly one source file.**

## Gems, ranked by surprise

### 1. `plainsong` — a 6,322-file golden-corpus regression discipline, and the best negative control in the fleet

**What it is.** A zero-dependency, PyPI-published (v1.6.0) plain-text music notation language that
compiles to MIDI and audio. 6,613 files, 33 test files, CI + release workflows, a VS Code extension,
a web worker, an MCP server, and a 5-provider LLM adapter registry. 23 CLI subcommands.

**Why another agent should care — the reason is not the music.** It solves *the fleet's own
canary problem* (`quilt-canary`, FNV-1a 64-bit) better than `quilt-canary` does:

- The fingerprint hashes **what notation compiles to** — pitch, position, length, velocity, voice —
  not the source text. It is a **semantic** canary, so a refactor that preserves text but changes
  sound is caught.
- The golden corpus is **6,322 committed digests** in `tests/corpus-fingerprint.txt`, checked in CI
  with `--check`.
- The docstring states the failure mode by name: *"`plainsong check` proves that notation still
  compiles; it says nothing about whether it compiles to the same notes. A change that moved every
  chord down a semitone would pass it cleanly."*
- Float canonicalisation is reasoned, not guessed: 6 decimal places, *"far finer than any musical
  distinction and far coarser than the noise"* — an explicit cross-platform float decision.
- Tracks are **sorted, not taken in arrangement order**, because order tracks are non-semantic.
- Digest is `sha256(...)[:16]` — 64-bit, the same width as the fleet canary.

The provenance note is the part worth stealing: the guarantee was originally established by a
hand-run script (*"181,276 identical, 136 newly readable, 0 changed"*) and *"the guarantee it
established stopped being checked the moment the script was closed."* So they moved it into CI.
This is the same lesson as *"a canary catches an editor who does not re-stamp; it never catches one
who does"* — institutionalised.

**Verified, not assumed.**

```
$ python -m plainsong fingerprint docs examples plainsong/songbook --check tests/corpus-fingerprint.txt
ok  6322 file(s) compile exactly as recorded          # exit 0, fresh clone, stdlib only
```

Compiled a test piece end-to-end; output is a genuine MIDI (`MThd`, format 1, 2 tracks, **24
note_on / 24 note_off**, matching the 24 notes `info` reported).

**Negative control — two mutations, and it correctly distinguished them.**

| Mutation | Result | Correct? |
|---|---|---|
| `key: C` -> `key: C#` (metadata only, `dialect: absolute`) | `ok 6322` | **yes** — semantic no-op |
| First chord `C` -> `C#` in `[intro]` | **exit 1**, `1 file(s) compile differently than recorded`, `was d1e3d2e12fa5189c / now bff876c65032221a` | **yes** — caught, named the file |

The first control is the interesting one: a naive checksum would have flagged it. A *semantic*
fingerprint correctly stayed silent, and the tool told you why (`dialect: absolute`). **This is a
golden corpus that knows the difference between a change and a no-op.**

**Structurally wrong:** nothing load-bearing. One note: 64-bit truncation is a detection choice, not
a security one — fine here, wrong if anyone promotes it to integrity.

### 2. `fm-experiments/consciousness-predictions` — the degenerate-measurement trap, caught live

**What it is.** Pre-registered predictions with recorded results (`results.json`), 7 predictions
about sheaf cohomology H1 and "consciousness as obstruction to gluing". Dated 2026-05-13.

**Why it matters.** This is the fleet's JEV/canon discipline (predict, then check) applied to
mathematics — and it is where I found the most transferable defect of the scout.

**The finding: the summary overstates the evidence by 2x.** `results.json` reports
`"passed": 4, "failed": 2, "na": 1`. The honest tally is **2 real passes, 2 vacuous passes, 2
fails, 1 N/A.** H1 is **0.0 in every trial, at every shard count** — the measurement is *constant* —
and a constant makes every relational predicate over it trivially satisfiable.

Two distinct vacuous-pass generators, both confirmed in source:

**P3** — `test_predictions.py:453`:
```python
passed = smaller == trials or (eq > 0 and smaller + eq == trials)
```
`smaller + eq == trials` is a tautology, and `eq > 0` holds whenever nothing is smaller. So the
prediction **"5-shard H1 < 3-shard H1" scores PASSED with `strictly_smaller: 0`, `equal: 8`**. Its
own `details` line prints *"Smaller in 0/8"* and then says PASSED. The literal claim is `0 < 0`.

**P5** — `test_predictions.py:565`:
```python
non_inc = all(h1_values[i] >= h1_values[i+1] for i in ...)
passed = non_inc
```
`[0, 0, 0, 0]` is trivially non-increasing. PASSED. `convergence_ratio: 0.0` confirms nothing moved.

Meanwhile the **headline hypothesis (P1, "3-shard H1 != 0") correctly FAILED** — 0/8 trials.

**The generalisable rule, and it belongs next to the digest discipline:**

> **A relational prediction requires a non-degenerate measurement as a precondition.**
> Score `std == 0` as INCONCLUSIVE, never as PASSED.

This is the *same disease* as the fleet's known "a constant hash is self-consistent" trap, one level
up: **a constant measurement makes every comparison true.** A check over a degenerate signal is not
a check. Any oracle in the fleet that can return a constant — a probe, a digest, a classifier —
needs a variance precondition before its verdict means anything.

**Structurally wrong:** the scoring rule, as above. `delta-detect` additionally cannot be run
unattended — it imports `torch` at module scope with no requirements file, so the README's
"GPU Needed: No / Run ~30s" is not reproducible from a clean checkout.

### 3. `fabric-mcp` — an unbuildable repository carrying its own broken git object store

**What it is.** 5,239 files, 100 MB, 177 test files, **54 languages**, no description. `package.json`
is named **`polln` v0.1.0** — *"Pattern-Organized Large Language Network"*. A very large amount of
ambition.

**Why it matters: nothing in this repo can build or test.** Verified:

- `tsconfig.json` `include` lists `src/**/*` + 11 more roots. **7 of the 12 are missing** —
  including `src/` itself, the primary one.
- **There is no `src/` at the root.** All 177 test files live under
  **`.git-rewrite/t/src/`** — a dot-directory no build script references.
- `.git-rewrite/` is a **committed raw git object store, 61 MB**: `HEAD`, `refs`, `commit`,
  `heads`, `revs`, `raw-refs`, `index`, and **`index.lock`**. `HEAD` is **empty**.
- `.git-rewrite/index.lock` is a lock file that should never be committed, and an empty `HEAD`
  means the "rewrite" was botched — this is the wreckage of a failed history rewrite, checked in
  wholesale.
- **No `.github/workflows` at root.** No CI.
- 4 Windows-path filenames committed at root (`C:Userscaseypollnspreadsheet-momentdocsFORK_STRATEGY.md`).

Consequence: `npm run build` (`tsc`) has no inputs; `npm test` (`jest`) has no tests at the
configured paths. All **100+ npm scripts** — including `bench:ci`, `test:e2e:visual`,
`lora:distill`, `scale:predict` — are dead on arrival. The elaborate tooling suggests an active
project; the tree says the source is not here.

**Structurally wrong:** everything above. The `claw/` subdirectory looks like a real, separate,
Dockerised project — the two need to be split apart.

**This is the same class as the known `quilt-i2i` defect, one level worse.** `quilt-i2i` has tests
that *could* run and no CI to run them. `fabric-mcp` has 177 tests the configured runner cannot
*locate*, in a repo carrying a corrupt git database.

### 4. Size is a lie, and here is the measurement that proves it

This is a methodology gem, not a repo. Ranking by `size` (KB) — the obvious proxy — produces these:

| Repo | Size rank | Blobs | Real source files | Committed build artifacts |
|---|---|---|---|---|
| `substrate-attest-rs` | **#24 / 4,890** (93 MB) | 434 | **1** (`src/lib.rs`) | 71 `.o`, 25 `.rlib`, 25 `.rmeta`, 40 `.d`, 92 `.timestamp` |
| `quilt-gpu-lab` | #14 (227 MB) | 1,103 | 156 | 58 `.rlib`, 58 `.rmeta`, 79 `.d`, 92 `.timestamp` |

`substrate-attest-rs` is **93% build output, including an entire `target/` directory** and ranks in
the fleet's top 25 by size. The other 4 "`.rs`" files in it are
`target/{debug,release}/build/serde-*/out/private.rs` — generated by the build system.

**Neither repo has any test.** (My first pass reported 102 "test" files in `substrate-attest-rs`;
that was my own false positive — the substring `test` matches `latest`. Worth stating so the next
scout filters on path segments, not substrings.)

**Action:** add `.gitignore` + `git rm -r --cached target/` to both. Until then, any substance
ranking that uses `size` is reading compiler output, not work.

### 5. `MicroMoth-quilt` — receipts have advanced past exp018 to a **SEALED** exp022

The brief says to read new `expNNN` files. They exist: **`exp019`, `exp020-tie-break`,
`exp021-r31-autopsy`, `exp022-desert-break`.**

`receipts/exp022-desert-break.json` is `status: SEALED`, schema
`micromoth-quilt/exp-receipt@v1`, and it carries three things worth borrowing as a pattern:

- **`vendored_sha256`** on the engine, with a note that it *"matches the import-baseline manifest
  pin on main"* — the receipt binds the **code that produced it**, not just the claim.
- **`seeds`** recorded exactly: streams, train/verify, shots, panel — reproducing a run is a
  documented procedure, not an archaeology exercise.
- A **`directive` field naming the previous experiment's blind spot** in its own words:
  *"exp021's Q2 opportunity census ran on exactly one stream — the canonical NON-crossing one
  (seed 31)."*

That third one is the strongest habit here: **each receipt is required to say what it could not
see.** That is the receipt-level version of the negative control, and it is more useful than the
pass/fail bit.

Result: the >=0.45 cell was train-visible on every r31 crossing stream at a single desert-break gen,
so root 31's crossing is a **per-stream desert-break rate (5/8 never birth one)**, not a tie-band
lottery; `RETENTION-ASSEMBLY` stands as the only no-break mechanism.

### The `.wrangler` one is worse than reported

`.gitignore` **now contains `.wrangler/`** — so it looks fixed. But:

```
$ git ls-files | grep -i wrangler
.wrangler/cache/wrangler-account.json
wrangler.toml
```

**The file is still tracked.** `.gitignore` only affects *untracked* files; it cannot untrack
anything. Someone added the ignore rule believing the leak was closed. It is not — the file is
committed, and it contains:

```json
{ "account": { "id": "049ff5e84ecf636b53b162cbb580aae6",
               "name": "Casey.digennaro@gmail.com's Account" } }
```

**Fix requires `git rm --cached .wrangler/cache/wrangler-account.json` + a commit**, plus a history
clean if the address is considered exposed. **A `.gitignore` entry is a claim about untracked files
only — never evidence that a tracked secret was removed.** Add this to the fleet's checkable list
next to the canary rule: a mitigation that does not change the tracked tree is not a mitigation.

## Reusable method notes for the next scout

- Authenticate first. Unauthenticated core quota (60/hr) dies at ~50 repos; this fleet needs 49.
- **Never filter forks when choosing targets** — `claw` and `MicroMoth-quilt` are both forks.
- Count source files by **extension + excluding `target/`/`dist/`/`node_modules/`**; `size` is
  compiler output more often than work.
- Match tests on **path segments**, not the substring `test` (`latest` false-positives hard).
- When a repo claims zero dependencies, that is *permission to verify it end-to-end* in a sandbox
  with no package index. It turned the strongest candidate from "readme says" into "ran it."
- A negative control needs a **semantic no-op** as well as a real mutation. `plainsong` passed both;
  a naive checksum would have failed the first.
